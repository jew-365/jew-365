# AGENTS.md

## Purpose

- Own persisted Zustand stores and persistence middleware.

## Ownership

- [useUserStore.ts](useUserStore.ts) owns user profile, location, language, theme (a `ThemeName`, `gold` by default), the display size (`uiScale`, one of the seven `UI_SCALES` steps of [../theme/scale.ts](../theme/scale.ts), `1` by default and for an older payload, so no `STORE_VERSION` bump; `setUiScale()` accepts only a step and leaves the state as it is for anything else, and the `merge` resets a saved value that is not a step to the default; the launch scale reads this field's persisted string once at launch, so a change, or a restore, takes effect at the next launch, which Settings forces with a reload; `reset()` returns it to `1`, and it rides the backup file with the rest of the store), permission, settings, onboarding state, the reader text size, the reader's auto-scroll (`siddurAutoScroll`, off by default, and `siddurScrollSpeed`, a 1-based level into the fifteen `SIDDUR_SCROLL_SPEEDS`, 5 to 150 lines per minute, that `scrollSpeedLevel()` keeps in range), `prayerMode` (`minyan` by default, or `alone`: whether the siddur folds what is said only with a minyan; Settings and the reader header write the same field), the `hilulotEnabled` switch for hilula notices (off by default), the `roshChodeshEnabled` switch for Rosh Chodesh notices (off by default; neither switch is in Settings, the library rows and their screens write them), the notice kinds of each topic (`hilulaNotices` and `roshChodeshNotices`, `{ enabled, daysBefore?, timing }` per kind with `timing` the shkia plus a lead of up to 180 minutes or a clock time, all on at the 2026-10-08 times by default; the two screens' notice cards write one kind through `setHilulaNotice()` and `setRoshChodeshNotice()`, and a switch with every kind off cannot be switched on, and the last kind cannot be switched off while its switch is on, both by the setter returning the state unchanged, as `setEnabled()` does for a mitzvah with no reminders), the `weeklyReportEnabled` switch for the weekly report notice (on by default, so an install saved before the field existed gets it on through the `merge`; Settings writes it, in the notifications block), the Chok LeYisrael double-week choice (`chokDoubleChoice`, `null` until a double week first asks, then `first`, `second` or `both`; the reader's sheet and its parashiyot row write it, and an older payload reads `null`), the Chok LeYisrael commentary choice (`chokCommentaryOpen`, `false` by default and for an older payload; the reader's toolbar and the Settings switch write it), the Chok LeYisrael ליל שישי day (`chokThuNightDay`, `null` until the reader's first "סיימתי" on ליל שישי asks, then `thu` or `fri`; the reader's sheet and the Settings chips write it, an older payload reads `null`, and it rides the backup file and the reset with the rest of the store), `gender` and `maritalStatus` (`married` or `single`), each `null` until answered, and the `taharahEnabled` opt-in. `noticeDaysBefore()`, `noticeTimingOf()`, `anyNoticeOn()`, `noticeChangeAllowed()` and `canEnableNotices()` are the one home of the notice rules.
- [useMitzvotStore.ts](useMitzvotStore.ts) owns enabled mitzvot and custom reminders, and `enabledAt`, the moment each was last switched on (`enabledSinceOf()`), so switching a mitzvah on never turns earlier days into misses. A missing `enabledAt` means since before it was recorded. Its `merge` also prunes the ids in `RETIRED_MITZVOT` (`tzitzit`, removed 2026-10-11) from the persisted map, so a mitzvah the registry no longer has never lingers in `getEnabledIds()`; custom ids pass through, and the retired id's completion rows stay in the completions store. A screen reads one mitzvah's state through `selectActive(id)`, which returns the frozen `INACTIVE` for an id the map lacks (a deleted custom mitzvah): a selector that built a fresh `{ enabled: false }` re-rendered without end. `stampEnabledNow(id)` sets `enabledAt` to now on an entry that is enabled and leaves the state as it is otherwise (the Selichot install restamps the mitzvah with it). A mitzvah that is switched on always has at least one reminder (the user's rule, 2026-10-24), and this file is the rule's one home: `remindersOf(state, mitzvah)` is a mitzvah's effective list (its `customReminders` when set, an empty list included, else its `defaultReminders`), `effectiveReminders(id)` reads it for a registry or custom id through `findAnyMitzvah()`, and `canEnable(id)` is true when it is not empty. `setEnabled` and `toggleEnabled` leave a mitzvah off when `canEnable()` fails (so `chooseGender()` cannot switch a men's mitzvah on without a reminder), `setReminders` ignores an empty list while the mitzvah is on, and switching off is never refused. The `merge` drops a persisted empty `customReminders`, so the defaults apply after a launch or a restore. Screens reach the rule through [../hooks/useNeedsReminderDialog.tsx](../hooks/useNeedsReminderDialog.tsx) and `remindersOf()`; none keeps a copy. `DEFAULT_ON_MITZVOT` is the default-on list (each id counts once it is in the registry). When a persisted map lacks a default-on id, the `merge` adds it with `enabledAt` at the hydrate's `Date.now()` and records it in `addedOnHydrate`; a default-off id comes back off and unstamped. A hydrate with nothing saved reads the user store's `isOnboarded`, which has hydrated by then (this file imports [useUserStore.ts](useUserStore.ts), which imports no store): an onboarded install that never wrote the store (a man who touched nothing in the library) and a restore from a file without it (`restoreBackup()` restores the user store first) start from `INSTALLED_DEFAULTS`, the five ids the first releases switched on, so only the newer default-on ids are stamped; a fresh install, not yet onboarded, starts from nothing, so every default-on id is stamped with its first launch and a new user is never asked about, or judged on, days before the install. `reset()` keeps the defaults unstamped, so `AppResetService` hydrates the store from nothing instead (after the user store is reset), and an in-app reset stamps like a first launch. Over the air this reaches a new user only from the second launch: the first launch of an install runs its build's embedded bundle (`updates` in [../../app.json](../../app.json) sets no `fallbackToCacheTimeout`), whose merge stamps nothing, so only a native build that carries this merge stamps from the first launch. A hydrate writes nothing while the saved version matches (on a mismatch zustand saves the merged map at once): `takeAddedOnHydrate()` hands the ids over once and writes the stamped map, and the first `applyGenderDefaultsToNew()` of every process, a headless one included, takes them.
- [useCompletionsStore.ts](useCompletionsStore.ts) owns completions and skipped maps, finished check-ins (`checkIns`, keyed by a block's first holy day) and `archivedDays`, the runs of kept days that retention dropped, `achievements` (badges by the day reached, longest streak, best week, each mitzvah's longest streak and the fold checkpoint; only ever raised, through `mergeAchievements()` / `saveAchievements()`) and `archivedMarks` (`archiveMarkCounts()`: the marks retention prunes, each day once by `lastKey`); `reset()` clears both.
- [useCustomMitzvotStore.ts](useCustomMitzvotStore.ts) owns user-created mitzvah definitions.
- [addonState.ts](addonState.ts) owns what every add-on store shares: `AddonStoreState` (`installed`, `latestVersion`, `checkedAt`, `download` and their setters), `IDLE_DOWNLOAD`, `selectAddonUpdateAvailable()` and `mergeSavedAddonState()`, the hydrate merge that keeps `installed` only when the files are present and starts the download idle.
- [useChokStore.ts](useChokStore.ts) owns the Chok LeYisrael add-on's install (`installed`: version, bytes on the device, install time and each parasha's file name, `.json.gz`, or `.json` for an install made before the compressed download), the latest version seen online (`latestVersion`) and when it was checked (`checkedAt`), plus, in memory only, the download progress (`download`: idle, downloading or failed) and the post-download enable prompt (`enablePrompt`: raised by `installChok()` when a first install ends with the mitzvah off, cleared by [../components/ChokEnablePrompt.tsx](../components/ChokEnablePrompt.tsx), by `clearInstalled()` and by `reset()`, and forced off by the `merge`). Only the first three persist (`partialize`), under `chok-store`. Its `merge` is the self-heal: it goes through `mergeSavedAddonState()` and keeps `installed` only when `chokInstallPresent()` finds the files, because an Android restore carries the store in the main MMKV file but not the files under `chok/`. `selectChokUpdateAvailable()` is true when the latest version seen is newer than the installed one. It is device-only: it is not in `STORES` of [../services/BackupService.ts](../services/BackupService.ts), and `AppResetService` resets it. Suite: [__tests__/chokStore.test.ts](__tests__/chokStore.test.ts).
- [useSelichotStore.ts](useSelichotStore.ts) owns the Selichot add-on's install (`installed`: version, bytes, install time and one file name, for the one nusach installed), the latest version seen online, when it was checked and `dismissedSeason` (the Hebrew year of the Tishrei that ends the season whose home offer was dismissed), plus the download progress in memory only. `partialize` keeps `installed`, `latestVersion`, `checkedAt` and `dismissedSeason`, under `selichot-store`. Its `merge` is the self-heal of `mergeSavedAddonState()` with `selichotInstallPresent()`. `selectSelichotInstalledFor(nusach)` says whether that nusach is installed and `selectSelichotNusach()` gives the installed one or `null`. `reset()` returns everything to null and the download to idle. It is device-only: it is not in `STORES` of [../services/BackupService.ts](../services/BackupService.ts), and `AppResetService` resets it. Suite: [__tests__/selichotStore.test.ts](__tests__/selichotStore.test.ts).
- [useSiddurBookmarksStore.ts](useSiddurBookmarksStore.ts) owns the siddur reader's bookmarks (`SiddurBookmark`: id, text id, nusach or `null`, section title, segment key, label, creation time) and each text's last reading position (`SiddurLastPosition`, one per text id: nusach or `null`, section title, segment key, app day, save time), under `siddur-bookmarks-store`. A bookmark list is newest first with one bookmark per text, nusach and segment: adding at a segment that has one replaces it. `textBookmarks()` and `textLastPosition()` are the one match rule: a record matches only when its text id and nusach are both equal, `null` matching only `null`, so Chok LeYisrael and the texts every nusach shares follow the user across a change of nusach. It is in `STORES` of [../services/BackupService.ts](../services/BackupService.ts) and `AppResetService` resets it. Suite: [__tests__/siddurBookmarks.test.ts](__tests__/siddurBookmarks.test.ts).
- [useTaharahStore.ts](useTaharahStore.ts) owns the taharah log (raw `TaharahEvent`s), the minhag settings (preset, per-rule overrides, role), the reminder lead times and the discreet-notification and lock switches. `addEvent()` ids are `taharah_<recordedAt>_<4 random base-36 characters>`, and a suffix already taken draws again, so two events in one millisecond never share an id. Everything shown about a cycle is derived from the events by [../utils/taharah/](../utils/taharah).
- [taharahOptIn.ts](taharahOptIn.ts) owns the cross-store opt-in calls: `chooseGender()`, `chooseMaritalStatus()`, `setTaharahTracking()`, `chooseNusach()` and `resetTaharahTracking()` (tracking off, `useTaharahStore.reset()`, then `clearTaharahStorage()`: the taharah reset path of the settings screen, so nothing outside taharah moves) write the user store, then apply the taharah store rule. `chooseGender()` also applies the gender defaults to the library: a change to `female` switches the registered ids of `MENS_MITZVOT` (`tefillin`, `kiddush_levana`) off, a change from `female` to `male` switches them on, and it sets the palette through `paletteForGender()` from [../theme/colors.ts](../theme/colors.ts), staying within the current light or dark class (gold or pink, dark or plum). Re-choosing the same answer touches neither, so a choice made in the library or a palette picked afterwards survives until the next change of gender. `taharahOffered()` is the one answer to whether the taharah topic is shown: a gender is chosen and the user is married. The onboarding steps and the Settings tab call only these, and read the offer through `taharahOffered()` only. `applyGenderDefaultsToNew()` takes `takeAddedOnHydrate()`, for a woman switches the men's ones off, and returns every id it took (the scheduler module drops its schedule stamp when the list is not empty); [../services/NotificationScheduler.ts](../services/NotificationScheduler.ts) calls it at module scope, so every native launch applies it right after this folder's stores hydrate, a headless background task or notification action included; the root layout calls it at load too (it covers web, whose scheduler is the shim, and finds the ids already taken on native), and `restoreBackup()` after the swap. `isMensMitzvah(id)` drives the library's `library.notForWomen` caption. `chooseNusach()` also stamps `enabledAt` now on every switched-on registry mitzvah the new nusach offers and the old one did not (Ushpizin, when a Chabad user moves to another nusach), so its earlier days never count as misses, the rule for a newly added default.
- [customMitzvahLifecycle.ts](customMitzvahLifecycle.ts) owns `reconcileEndedCustomMitzvot(now?)`: it switches off every enabled custom mitzvah whose current range or streak ended before today's app day and returns their ids; the definition, completions and skips stay. It lives here because it writes a store, which [../utils/AGENTS.md](../utils/AGENTS.md) forbids, and outside [useCustomMitzvotStore.ts](useCustomMitzvotStore.ts), which the mitzvot store reaches through the custom adapter, so importing it there would close an import cycle.
- [zustandMiddleware.ts](zustandMiddleware.ts) owns Zustand middleware interop.
- Store tests live in [__tests__/](__tests__/).

## Local Contracts

- Stores persist through MMKV using [../services/StorageService.ts](../services/StorageService.ts). The one exception is `useTaharahStore`, which persists to its own encrypted instance through [../services/TaharahStorage.ts](../services/TaharahStorage.ts). Taharah data never goes into a plain store, and nothing outside this store and its reset path imports `taharahStorage`.
- Keep persisted defaults, reset behavior, and migrations/backward compatibility in sync when adding fields.
- A backup file carries each plain store's persisted string, and a restore rehydrates it through the store's own `migrate` and `merge` ([../services/BackupService.ts](../services/BackupService.ts)), so a file from an older release goes through the same path as an old install. A new store joins `STORES` there unless it is device-only or sensitive, and every store keeps a `reset()`, which a restore calls for a store the file lacks.
- Every `persist()` passes `migrate` from [persistOptions.ts](persistOptions.ts), the identity until a real shape change needs a step: zustand drops the whole persisted state on a version mismatch without one. The store tests pin it per store through `store.persist.getOptions()`.
- `locationStatus` starts as `missing`: the default city is a guess until GPS or a city pick writes `ready`, and home shows the no-location banner until then.
- Every `persist()` passes `version` and `onRehydrateStorage` from [persistOptions.ts](persistOptions.ts). A store that persists somewhere other than the plain MMKV instance passes that storage as the second argument, or a corrupt payload is dropped from the wrong place and fails again next launch. A store whose state is a keyed map also needs a `merge` that unions the current defaults back in, or entries added in a later release never reach existing users; `useTaharahStore` does that for `settings.rules`, filling a missing rule from the saved preset; a saved preset id this build does not know (a rollback) falls back to the current preset label while the saved rules, events and leads are kept, because a throw inside `merge` drops the whole store.
- A new top-level field on a store merges in through zustand's default shallow merge, so adding one (`gender`, `maritalStatus`, `taharahEnabled`) needs a default and a `reset()` entry but no `STORE_VERSION` bump. [useUserStore.ts](useUserStore.ts) has a `merge`, `mergeSavedUserState`, only to repair an old payload. It infers `maritalStatus`: a saved payload with `taharahEnabled` on and no status reads as `married`. It also maps a saved `theme`: a known name is kept, the legacy `system` becomes `dark` when the OS appearance is dark at hydrate time and `gold` otherwise, and the legacy `light` and anything unknown become `gold`. It also fills `hilulaNotices` and `roshChodeshNotices` from the defaults (a missing map or kind reads as its default, a kind this build does not know is dropped) and restores the defaults of a topic whose switch is on with every kind off, so no `STORE_VERSION` bump.
- A saved city is never a frozen snapshot: `mergeSavedUserState` re-resolves the saved `location` from `CITIES` on every hydrate through `refreshSavedLocation(location, locationSource)` in [../data/cities.ts](../data/cities.ts) (by `cityId`, or by name for a snapshot saved before ids existed; a manual pick becomes the current entry, a GPS fix keeps its own `lat` / `lng`, a location matching no city is left alone) and sets `inIsrael` from the result, as `setLocation` does. A corrected latitude, zone, elevation or candle-lighting minutes in `CITIES` thus reaches an existing install on its next launch. `merge` runs on every hydrate, so this needs no `STORE_VERSION` bump and no migration step; the hydration cases are pinned in [__tests__/stores.test.ts](__tests__/stores.test.ts).
- `useTaharahStore` is the only place a gender or a nusach becomes a taharah role and preset: `startTracking(gender, nusach)` (tracking switched on), `setRoleForGender(gender)` (gender changed while tracking) and `adoptPresetFor(nusach)` (nusach picked in onboarding). A preset is adopted only while the store is untouched, meaning no events and rules identical to the current preset's own, so a hand-edited rule or a recorded cycle is never overwritten; the guard exists once, here, and no screen repeats it. Screens reach these actions only through [taharahOptIn.ts](taharahOptIn.ts), so the gender, marital status, tracking and nusach rules cannot drift between onboarding and Settings.
- Tracking is switched on only through `setTaharahTracking()` while `taharahOffered()` holds; a call outside the offer is ignored and writes nothing. `chooseMaritalStatus()` with anything but `married` switches tracking off while it is on, and the taharah store keeps its events and settings.
- `siddurVoice` in [useUserStore.ts](useUserStore.ts) (`male`, `female` or `null`, `null` by default and for an older payload) is the siddur's voice. `chooseGender()` sets it to the new gender on every change of gender, overwriting a choice made in Settings; re-choosing the same gender leaves it. The Settings chips write it through `setSiddurVoice()`, and the reader passes it to `forVoice()` and the siddur tab to `catalogListsText()`, both in [../utils/siddur.ts](../utils/siddur.ts). An install that answered the gender before the field existed keeps `null` until its gender changes or a chip is tapped.
- `AppResetService` resets `useTaharahStore` and then wipes its storage and replaces its key with `clearTaharahStorage()`; a new taharah field needs a default in `initialData()` so that reset covers it.
- Completion maps are pruned to `RETENTION_DAYS` on hydrate and must never write empty day buckets. The days pruned away are folded into `archivedDays` first (`archiveMarkedDays()`), and finished check-ins are pruned with the same cutoff.
- `finishCheckIn()` is idempotent and withdraws the block's check-in reminders through the same queued `require()` the completion actions use. `markDone` and `markSkipped` queue `cancelForMitzvah()` and `settleCheckIn()` behind `afterPaint()` ([../utils/afterPaint.ts](../utils/afterPaint.ts): after the next frame and idle time; a headless mark awaits the cancel and the settle itself in `markDoneFromNotificationData()`), so the mark that empties a check-in withdraws its reminders too.
- A completion or skip is keyed by the day its window was computed for, `dateKey(window.date)`, the key that window's notifications carry: after midnight a night window (maariv, the Omer, a custom window across midnight or one wholly before alot) still belongs to the previous date. A screen always passes that date to `markDone`, `markSkipped` and `unmark`, never `dateKey(new Date())`; the `date = new Date()` defaults of the actions and selectors serve tests only.
- `useCompletionsStore.markDone`, `markSkipped`, and `unmark` must preserve notification cancellation/rebuild side effects.
- Do not replace the deliberate `../../node_modules/zustand/middleware.js` require in [zustandMiddleware.ts](zustandMiddleware.ts) unless Metro and Jest are both verified.
