# AGENTS.md

## Purpose

- Own non-React app logic and native-facing service wrappers.

## Ownership

- [ZmanimService.ts](ZmanimService.ts) owns kosher-zmanim calculations and caching, the per-location candle-lighting minutes (`candleLightingMinutes()`, `isJerusalem()`, which reads `cityId === 'jerusalem'`, never a display name) and the Shabbat / Yom Tov exit margin (`HOLY_BLOCK_EXIT_MIN`, `holyBlockExit(zmanim)`: ten minutes after tzeit, the user's call on 2026-10-10). They live here, below every caller, so no service imports the mitzvah registry and no require cycle forms.
- [HebcalService.ts](HebcalService.ts) owns Hebrew calendar, holidays, Shabbat, chol hamoed, holy blocks, Daf Yomi, and Omer logic (`getHolidays()` and `getParasha()` take a `CalendarLocale`: `he` with vowel points, `en`, or `he-x-NoNikud`, the form the notices and the weekly report print; `getHolidays()` takes a fourth argument `{ cholHamoed?, erev?, omitChanukahCandles?, omitChanukahDay? }`: the first two add chol hamoed days, Hoshana Raba included, and erev days to the list, off by default so the schedule and the reader keep their lists, and the weekly report's next week turns both on; `omitChanukahCandles` drops hebcal's Chanukah candle labels (`flags.CHANUKAH_CANDLES`, each naming the candles lit on the evening of the civil day it sits on), which the reader's header replaces with its own night; `omitChanukahDay` drops its "Chanukah: 8th Day" label, which the header leaves out only while that night is named), and `nightfall(zmanim, loc)`: when the night after a day opens, its tzeit, or the block's exit on the last day of a holy block, which every night window of that day (maariv, the Omer, havdalah, a tevila) takes as its start.
- [LocationService.ts](LocationService.ts) owns location access wrappers. A GPS fix within 25 km of a `CITIES` entry borrows that city's `cityId`, name, zone, `inIsrael`, elevation and `candleLightingMinutes` and keeps its own latitude and longitude; a far fix carries none of them. `getLastKnownPoint()` (the device's last fix, 30 minutes old at most) and `getPrecisePoint()` (a high-accuracy fix with `mayShowUserSettingsDialog: false`, 20 s at most) return bare coordinates or `null` and never reject; the prayer compass uses them. `getCurrentLocation()` (Settings' "locate me" and the onboarding location step) asks for the same high-accuracy fix with `mayShowUserSettingsDialog: false`, because with the network provider off Android's Location Accuracy dialog rejected the request once it was declined (2026-10-27), and when that fix fails it falls back to `getLastKnownPoint()` before reporting `timeout` or `missing`.
- [StorageService.ts](StorageService.ts) owns MMKV-backed storage helpers.
- [BackupService.ts](BackupService.ts) owns the backup file: `createBackup()` (the persisted strings of `user-store`, `mitzvot-store`, `completions-store`, `custom-mitzvot-store` and `siddur-bookmarks-store`, never `taharah-store`), `parseBackup()` (throws `BackupError` `invalid` for anything that is not a backup of an app in `RESTORABLE_APPS` (this app's tag, then the previous app's) with a user store and well-formed payloads, `newer` for a format above `BACKUP_FORMAT`; unknown store names are dropped), `restoreBackup(backup, options?)`, `reloadIfScaleChanged()`, `exportBackup()` (a dated `jew-365-backup-<YYYY-MM-DD>.json` in the cache directory, handed to `expo-sharing`), `pickBackup()` (`File.pickFileAsync()`; null when the picker is closed, `invalid` above 5 MB), `backupDateLabel()` and `backupFailureKey()`, which maps a failure to its `settings.backup*` message and reports an unexpected one under scope `storage`. `expo-sharing` is native, so it ships with a build. Suite: [__tests__/BackupService.test.ts](__tests__/BackupService.test.ts).

- [ChokContentService.ts](ChokContentService.ts) configures the shared core of [addons/addonContent.ts](addons/addonContent.ts) for the Chok LeYisrael add-on's download from `CHOK_BASE_URL` (`https://jew-365.github.io/jew-365/chok/`, GitHub Pages). `parseChokManifest()` accepts a manifest only with `CHOK_FORMAT`, the 54 parashiyot in `gz` (`.json.gz`) and in `files` (`.json`) when the manifest has `files` (it is optional, with its `bytes`: the app reads only `gz`), content-addressed paths, SHA-256 hashes, and `gzipBytes` (and `bytes`, with `files`) sums that agree; `fetchChokManifest()` bypasses the host's cache with `?t=` and times out after `CHOK_REQUEST_TIMEOUT_MS`; `prepareChokDownload()` returns the manifest for the confirmation dialog or records a failure; `installChok()` is single-flight (a second call gets the running promise), never rejects, checks the free space (`CHOK_SPACE_MARGIN_BYTES` over the manifest's `gzipBytes`), downloads each parasha's gzip (`gz`) as bytes straight into `chok/v<version>`, kept compressed, with `Cache-Control: no-store` and `Pragma: no-cache` on every file request so the platform's HTTP cache (OkHttp's `cache/http-cache` on Android) neither keeps a second copy of the 5 MB nor serves a download after a delete from itself (the manifest request keeps its `?t=` and the default cache), with `CHOK_FILE_ATTEMPTS` attempts and a growing `CHOK_RETRY_DELAY_MS`, and checks the SHA-256 of those bytes with `expo-crypto`'s `digest()`; the install records the `.json.gz` names and `gzipBytes`. A download that started with nothing installed and ends in an install raises `useChokStore.enablePrompt` while `chok_leyisrael` is off; an update, a download of the installed version again, a failure, a cancel or a mitzvah already on raises nothing. `switchChokOn()` is the prompt's yes: it restores the default reminders through `resetToDefault()` when the mitzvah has none (`canEnable()` false), then calls `setEnabled(CHOK_TEXT_ID, true)`, which stamps `enabledAt`. The install is recorded only after every file verified (the record is the switch): a failed update leaves the installed version untouched and a failed first download deletes its directory, and no directory is ever renamed (Android API 24-25 copies a renamed directory without its contents). After the record it deletes every other entry of `chok/` and clears the reader's cache. A failure is `'space'` only for the free-space check (`CHOK_SPACE_NEEDED_MB`, the manifest-size estimate plus `CHOK_SPACE_MARGIN_BYTES`, is what the screens quote) and `'storage'` for a failed directory create or file write; a cancel up to the switch wins. `cancelChokDownload()` aborts it, `deleteChok()` cancels, forgets the install (`forgetChokInstall()`: clears the record and the reader's cache and switches the mitzvah off) and deletes the files, `checkChokUpdate()` asks for the manifest at most once a day (`CHOK_CHECK_INTERVAL_MS`) while installed, stamps a failed attempt too and never rejects, and `verifyChokInstall(readError?)` forgets an install whose files are gone or whose read failed with `ChokFileCorruptError` (reported under scope `storage`), so the screens offer the download again. `reconcileChokInstall()` runs at launch (the root layout) and after a backup restore, never throws and does nothing while a download runs or on web: it forgets an install whose files are gone, switches the mitzvah off while nothing is installed (so a later install and switch-on starts history afresh, and history never judges days without the add-on) and deletes every leftover in `chok/` but the installed version. `CHOK_SIZE_ESTIMATE_MB` is the size the screens show before the manifest is fetched, the download and the size on the device alike; a test pins it to the `gzipBytes` of [../../docs/chok/manifest.json](../../docs/chok/manifest.json). On web nothing downloads (`chokDownloadSupported()`). Suite: [__tests__/ChokContentService.test.ts](__tests__/ChokContentService.test.ts).

## Local Contracts

- Keep [NotificationScheduler.ts](NotificationScheduler.ts) and [NotificationScheduler.web.ts](NotificationScheduler.web.ts) API-compatible.
- Preserve notification identifiers as `${mitzvahId}__${YYYY-MM-DD}__${reminderIndex}`, with `.${n}` after the index for the n-th further trigger of a `blockExit` reminder (`buildId(..., occurrence)`; `parseId()` reads the index as an integer), unless all scheduler, response, and tests are updated together. A notification not tied to a mitzvah (the pre-block notice, `blockNotice:<YYYY-MM-DD>`, the check-in reminders, `checkin:<YYYY-MM-DD>:<n>` with `data.blockId`, the update notice, `update:<update id>` with `data.updateId`, the hilula notices, `hilula:<hebrew abs day>:<before|evening>` with `data.hilula = { day, when, ids }` (the ids of the tzaddikim the notice names, in order), and the Rosh Chodesh notices, `roshChodesh:<hebrew abs day>:<before|evening|day>` with `data.roshChodesh = { day, when }`, and the weekly report notice, `report:<YYYY-MM-DD of the week's last day>` with `data.report = { week }`, and the end-of-reminders notice, `horizonEnd:<YYYY-MM-DD of the last fully planned day>` with `data.kind = 'horizonEnd'`) uses an id without `__` and a `data.kind`, so `parseId` and every mitzvah lookup ignore it, and it carries no category (the taharah bedika reminders are the one exception, below).
- Android channels are `ANDROID_CHANNELS`, exported from both scheduler files. `ensureChannels()` in [notifications/os.ts](notifications/os.ts) creates all five (on a rebuild, a permission request and an update notice) and every candidate names one by `ChannelKey`, so a new kind of notification picks its channel in the same change:

  | id | name key | importance | lock screen | carries |
  | --- | --- | --- | --- | --- |
  | `default` | `notifications.channelName` | HIGH, vibration pattern, LED colour | PUBLIC | mitzvah reminders, the pre-block notice |
  | `hilulot` | `hilulot.title` | DEFAULT, no vibration pattern | PUBLIC | hilula notices |
  | `rosh-chodesh` | `roshChodesh.title` | DEFAULT, no vibration pattern | PUBLIC | Rosh Chodesh notices |
  | `taharah` | `taharah.home.title` | HIGH, no LED colour | PRIVATE | taharah reminders, the merged pre-block notification |
  | `system` | `notifications.channelSystem` | DEFAULT | system default | check-in reminders, the weekly report notice, the update notice, the end-of-reminders notice |

  The mitzvot channel keeps the id `default`: a channel's sound and importance are the user's once it exists, and they follow the id.
- Check-in reminders come from `checkInFor()` in [../utils/checkIn.ts](../utils/checkIn.ts), for every block in the horizon and the three days before it, and are never scheduled for a finished check-in or one with nothing left to mark. They fire at the block's exit, two hours later, and as a last call at 20:00 on the location's clock the day after the block (half an hour before the next block's candle lighting when that evening is already holy), never at or after the check-in's deadline: the alot that ends the first weekday after the block, `checkInDeadline(block, location)`. `cancelCheckIn()` clears them from the tray and withdraws the rest through `rebuild()`, so a rebuild already in flight, which read the old state, is re-run instead of re-adding them. `settleCheckIn(date)` does the same after any mark or skip that leaves the day's check-in with nothing to mark; both are mirrored in the web shim. `shouldSuppressForCompletion()` and `dismissCompletedPresentedNotifications()` treat a settled check-in — finished, or nothing left to mark — like a done mitzvah.
- `MARK_DONE` must stay aligned with [../../scripts/withMitzvahNotificationAction.js](../../scripts/withMitzvahNotificationAction.js).
- Hilula notices exist only while `useUserStore.hilulotEnabled`. For each horizon day, `hilulaNoticesOn()` takes the Hebrew day whose daytime is that civil date (`civilHebrewDayAt()`, never the zmanim-driven `hebrewDayAt()`, which an Arctic winter shkia before noon pushed a day ahead) and plans the kinds switched on in `useUserStore.hilulaNotices`: `evening` for the hilulot of the next Hebrew day (it opens at this shkia) and `before` for those that open `noticeDaysBefore()` evenings later (`HILULA_BEFORE_DAYS`, 1 by default, 1–7, so `before` and `evening` never fall on one day). Each fires at `noticeTriggerAt()` of its `timing`: the shkia or up to 180 minutes before it, or a clock time on the location's clock. The text follows how far ahead the date opens: `evening.*` when it opens this evening, by `noticePhase()` against that shkia: `bodyTonight` before it, `evening.body` at it, `evening.titleBegun` / `bodyBegun` after it; `before.*` when it opens the next evening; `before.titleOn` / `bodyOn`, naming the weekday, further out, and the date with it (`noticeDayLabel()` in `planners/horizon.ts`) from seven days out, where a bare weekday would read as today. Names join in the registry order, in the UI language. A notice whose time is past or inside a holy block is not scheduled; `hilulaLines()` names each one a block swallows, once per Hebrew day, in the pre-block notice: `holyBlock.notice.hilulaTonight` when the date opens on the erev, else `hilulaOn` with the weekday it opens, and its date when that is seven days or more after the erev. A change of `hilulotEnabled` or `hilulaNotices` rebuilds the schedule.
- Rosh Chodesh notices exist only while `useUserStore.roshChodeshEnabled`. For each horizon day, `roshChodeshNoticesOn()` takes the Hebrew day whose daytime is that civil date (`civilHebrewDayAt()`) and plans, on the `rosh-chodesh` channel: the kinds switched on in `useUserStore.roshChodeshNotices`: `before` when the Rosh Chodesh begins `noticeDaysBefore()` Hebrew days later (`ROSH_CHODESH_BEFORE_DAYS`, 3 by default, 1–7), `evening` when it begins tonight, and `day` on every Rosh Chodesh day, each at `noticeTriggerAt()` of its `timing` (by default 20:00 on the location's clock, the day's shkia and 07:00). A two-day Rosh Chodesh begins on the 30th, so its lead notices count from day one and its `day` notice fires on both days; a month with no 30th before it has one day. The title names the new month (`roshChodeshLabel()`), the `before` title the days left (`roshChodesh.notice.inDays.<n>`), and the body of a `before` notice names the weekday of the evening the month enters, or `before.bodyTonight` one day ahead; a `before` or `evening` notice after the shkia that opens the month (`noticePhase()`) takes `roshChodesh.notice.begun.title` / `begun.body`, and `day` keeps `day.*`. A notice whose time is past or strictly inside a holy block is not scheduled; `roshChodeshLines()` names each one the block swallows in the pre-block notice, once per month for the lead notices and once per day for `day`; a lead line names the date with the weekday when the month enters seven days or more after the erev (`noticeDayLabel()`). A change of `roshChodeshEnabled` or `roshChodeshNotices` rebuilds the schedule.
- The weekly report notice exists only while `useUserStore.weeklyReportEnabled` (on by default). `planReport()` takes every block in the horizon and the three days before it whose `weekEndFor()` is not null (it holds a Saturday: motzaei Shabbat, or a Yom Tov that follows Shabbat, whose last day is then the week end; a mid-week Yom Tov has none) and schedules `report:<week end>` on the `system` channel at the block's exit plus `REPORT_DELAY_MIN` (45) minutes, after the check-in's first nudge (at the exit) and before its second (two hours on). The payload is `data.report = { week }`, the week end's date key; no category. A trigger that is past or strictly inside another block is not scheduled, and a rebuild during the 45 minutes still plans it. A change of `weeklyReportEnabled` rebuilds the schedule.
- Taharah reminders exist only while `useUserStore.taharahEnabled`. `planTaharah()` maps each horizon day's `taharahTasksFor()` tasks to `data.kind = 'taharah'` notifications, `data.taharah = { task, day, onah? }` with `day` the Hebrew abs: `hefsek` at the task's end minus `hefsekLeadMin`; `bedikaMorning` at sunrise plus 30 minutes and `bedikaEvening` at its end minus `bedikaEveningLeadMin`, both skipped once marked; `tevilaPrep` at the tevila task's start minus `tevilaPrepLeadMin` plus `tevila` at that start (tzeit, or the block's exit on motzaei Shabbat / Yom Tov, from `HebcalService.nightfall()`); `perisha` at the onah's start; `bedikaVeset` an hour before the onah ends, only when it is required (the onah beinonit is among its reasons); `expectOnset` at 10:00 on the location's clock; and, for a woman only, `postBlock` 15 minutes after a holy block that left a clean day's bedika slot unmarked. Ids carry no `__`: `taharah:<task>:<day>`, `taharah:<task>:<day>:<night|day>` for `perisha` and `bedikaVeset`, `taharah:postBlock:<YYYY-MM-DD>`, `taharah:preBlock:<YYYY-MM-DD>` (the merge below); a repeated id keeps the first.
- With `discreetNotifications` (the default) every taharah notification shows only the neutral `taharah.notify.discreet*` text; otherwise it reads `taharah.notify.title.<task>` / `body.<task>`, with the disputed line when the onah is in dispute.
- `beforeQuiet()` is the one rule for taharah triggers: a trigger strictly inside a holy block goes out ten minutes before the block's candle lighting instead, unless the task's own window (`TaharahDraft.end`) outlasts the block, when it waits for the block's end (a perisha night opening at motzaei Shabbat's shkia fires at the exit); a trigger not after now is dropped. A `tevila` whose own trigger is inside a block is replaced by its `tevilaPrep` alone, worded by `tevilaPrepShabbat` and naming candle lighting; the reminder for the later night still fires at the block's end.
- Drafts that `beforeQuiet()` pulled ahead of a block are grouped by the block they were moved out of, `quietBlockAt(draft.trigger).days[0]`; unshifted and deferred drafts are scheduled one by one. Every group, a lone draft included (its own text would name a deadline inside the block), becomes ONE notification: `taharah:preBlock:<first day of the block>`, `data.taharah = { task: 'preBlock', day }` with `day` the Hebrew abs of the block's first day (`firstDayAbs()`, shared with `postBlock`), no category, at the shifted instant. Discreet it reads `discreetTitle` / `discreet.preBlock`; otherwise `title.preBlock` with the block's `checkin.in.*` phrase, and a body of each member's own non-discreet title in the order the originals were due, repeated titles once, plus `taharah.disputed` once if any member is disputed. The members' own bodies (`tevilaPrepShabbat` included) are dropped in the merge.
- Only `bedikaMorning` and `bedikaEvening` carry the `taharah_bedika` category, one `MARK_DONE` button titled `taharah.notify.markDone`; no other taharah reminder has a category, so a hefsek or an immersion is only ever entered in the app. `markDoneFromNotificationData()` handles that button before any mitzvah lookup, in the headless action task too, by recording a clean `bedika` event for the slot, unless the slot already has a result, and dismisses the notification.
- `taharahNotificationSettled(data)` replays `deriveCycle()` over the store's events at the moment of asking: a bedika is settled when its clean day has no such slot left or the slot has a result, a `hefsek` once the cycle is past the hefsek stage, a `tevila` / `tevilaPrep` once the stage is `tahor`, a `postBlock` once no clean day in that block lacks a slot, an `expectOnset` once the latest onset is on or after its day; `perisha`, `bedikaVeset` and `preBlock` never. `shouldSuppressForCompletion()` and `dismissCompletedPresentedNotifications()` use it.
- `initNotificationHandlers()` also rebuilds on a `useTaharahStore` change of events, settings, the discreet switch or any lead, while `taharahEnabled` is on, and on a change of `taharahEnabled` itself. It rebuilds too when `useChokStore.installed` turns from null or to null, because the window of Chok LeYisrael exists only while the add-on is installed, and when the nusach of `useSelichotStore.installed` changes (`selectSelichotNusach()`), because the Selichot window exists only for an installed nusach.
- The daily rebuild is an `expo-background-task` task named `jew-365-daily-rebuild` (`DAILY_REBUILD_TASK` in [notifications/ids.ts](notifications/ids.ts)), registered with `minimumInterval: 60` (minutes; the OS decides the real cadence, 15 at the least). Its body returns `BackgroundTaskResult.Success` or `.Failed`. A failed registration is logged and never thrown. The web shim keeps the same name. The notification action task is unchanged and keeps its own result codes (`BACKGROUND_NOTIFICATION_RESULT`). Every run first withdraws the presented mitzvah reminders whose app day has ended ([notifications/AGENTS.md](notifications/AGENTS.md)); a failure there never fails the task.
- `notifyIfUpdateReady(now)` runs at the end of every `DAILY_REBUILD_TASK` run (a failed check is logged with `console.warn` and never fails the task): it downloads a newer update through `downloadNewUpdate()` and presents one notice per update id, remembered under `UPDATE_NOTIFIED_KEY` only after the notice is scheduled, and withdraws the previously remembered notice first, so the tray holds one update notice at most and a run skipped for a holy block (`isQuietAt()` once onboarded), a switched-off notifications setting or a denied permission (`hasNotificationPermission()`) retries next hour. Title `update.notice.title`, body `home.updateReady`, Android on the `system` channel, immediate trigger. A notice carries `data.updateId` and `data.updateCreatedAt`; one whose update, or a newer one, is already running (`isUpdateApplied()`) is stale: `shouldSuppressForCompletion()` hides it and `dismissCompletedPresentedNotifications()` clears it from the tray at the next launch. `SCHEDULE_FORMAT` is unchanged: the notice is presented, never left pending.
- A reminder gets the `mitzvah_reminder_text` category (`OPEN_TEXT` + `MARK_DONE`) exactly when `hasSiddurText()` is true for its window date and its trigger is not a holy block's opening edge (`opensQuietBlock()`); otherwise `mitzvah_reminder`. `OPEN_TEXT` opens the app to the reader and needs no native handling; the Android plugin only dismisses on `MARK_DONE`. The same decision is the payload's `data.hasText` (true exactly when the text category is chosen), which routes the body tap.
- Category button titles are translated, so a language change rebuilds; it is part of the user-store subscription.
- Raise `SCHEDULE_FORMAT` whenever the shape of a scheduled notification changes (category, actions, payload). A rebuild deletes the stamp before it touches the schedule and writes it back when done, and a foreground with a missing or stale stamp rebuilds once — so an update, or a rebuild cut short by a reload (a language switch reloads the app for RTL), is redone; otherwise reminders already scheduled by the previous bundle keep the old shape until the next day. It is raised too when a mitzvah leaves the registry (`tzitzit`, 2026-10-11), so the `<id>__…` reminders already scheduled for it are cleared on the first foreground. It is raised too when a payload gains a field every scheduled notification carries (`contentHash`, 2026-10-26). It is raised too when a notification's text was wrong on a platform (weekday names that read "null" on iOS, 2026-10-24), so the texts already scheduled are rewritten. A mitzvah the mitzvot hydrate switches on needs no raise: the module scope drops the stamp when `applyGenderDefaultsToNew()` returns any id, and the dropped stamp outlives the process, so a headless launch that took the ids without rebuilding still leaves the rebuild to the next foreground; pinned by [NotificationScheduler.headless.test.ts](__tests__/NotificationScheduler.headless.test.ts).
- `cancelForMitzvah(id, date)` and `settleCheckIn()` share one read of the pending list when a mark starts both at once (`readScheduled()`). `cancelForMitzvah(id, date)` must cancel all pending reminders for that mitzvah/date and dismiss the ones already in the tray; every done and skip path relies on it.
- Always pass `Location` to `HebcalService.isShabbat(date, location)` when halachic boundary behavior matters.
- Holy blocks: `holyBlockAt(instant)` returns the block whose [candle lighting, exit] span contains the instant, edges included, the exit being `holyBlockExit()` of the last day (tzeit itself is still inside); `isHolyDay(date)` and `holyBlockOn(date)` are day-granular, judging the location's calendar date of `date` by its daytime. A block merges every touching Shabbat / Yom Tov / Yom Kippur day. Per-day holiday flags are memoized per Hebrew day and `inIsrael`.
- `isShabbat` and `isYomTov` both derive from one internal `hebrewDaysAt(instant, loc)` primitive. Its civil day is the instant's date in the LOCATION's zone, the same day `ZmanimService` resolves, never the device's. A Hebrew day turns over at shkia, and between shkia and tzeit both candidate days are returned so an observance counts if either carries it. Do not reintroduce a Gregorian-day check for either. The exit margin does not move the Hebrew date: at tzeit plus five minutes on motzaei Shabbat the date is Sunday while `holyBlockAt()` still answers the block, and no window starts in that gap because the night windows of a block's last day open at `nightfall()`.
- Use `getHebrewDateAt(instant, loc)` for "today" displays (it advances at shkia) and `getHebrewDate(date)` only for calendar grids, where each cell is a civil day. `hebrewDayAt(instant, loc)` is the same day as an `HDate`, for a text that resolves "now": from shkia on, bein hashmashot included, it is the next day. `hebrewNightAt(instant, loc)` is the Hebrew day whose night is in effect or comes next, for a text said at night: before dawn (alot hashachar) the night still running, from dawn on tonight's. Dawn is `dawnAt(instant, loc)`, the alot of the location's calendar date of `instant`, or 04:00 on the location's clock (`DAWN_FALLBACK_HOUR`) where the sun neither rises nor sets: the one home of that boundary, which the app's day (`appDay()` in [../utils/locationDay.ts](../utils/locationDay.ts)) and Chok LeYisrael's learning day also turn at.
- Avoid UTC date shortcuts for mitzvah logic.
- `Zmanim.chatzotLayla` is chatzot halayla (solar midnight) of the night FOLLOWING that day, which falls before 00:00 in some seasons and places (23:44 in Jerusalem on 2026-03-26) and after it in others (00:39 on 2027-06-15). It ends a window that closes at midnight; a window that runs all night (maariv, the bedtime Shema, the Omer, Chok LeYisrael) ends at the next day's `alotHaShachar` through `nextAlot()` in [../data/mitzvot.ts](../data/mitzvot.ts).
- Battery-optimisation exemption is the user's half of reliable delivery; the request goes through `requestIgnoreBatteryOptimizations()`: the system dialog first (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`), then the battery list, then the app's settings page. Google Play reviews that permission (the owner's call, 2026-10-28).
- Exact-alarm delivery depends on the Android manifest, not on any runtime call; see the root AGENTS.md notification section before touching `android.permissions` or the config plugins.
- `ZmanimService` resolves the calendar day in the LOCATION's zone (`setDate` with a zoned Luxon DateTime, cache keyed on that ISO date). Never hand it a bare `Date`. Its zmanim cache is least-recently-used at 400 entries (a hit moves the entry to the newest slot), enough for a launch that reads home's Selichot offer, history, Kiddush Levana and the siddur tab together, and the civil day of a key comes from a per-zone map of 15-minute buckets, so a hit does no Luxon `setZone` work (an offset or a transition is always a whole 15 minutes, so a bucket never straddles a local midnight); a read still returns a copy. It overrides the GeoLocation's `getAntimeridianAdjustment()` with `antimeridianAdjustment(loc)`, the same 20-hour check computed from the zone's true standard offset: kosher-zmanim 0.9.0 (the latest) flips the sign of the raw offset for every zone that keeps DST, which rolled Sydney, New Zealand and the Aleutians a day forward. Nothing else the app calls reads that offset. Pinned by the day-resolution tests in [__tests__/ZmanimService.test.ts](__tests__/ZmanimService.test.ts); recheck after a kosher-zmanim upgrade.
- `initNotificationHandlers()` runs the launch permission sync, the tray clean-up and `refreshSchedulingOnForeground()` behind `afterPaint()` ([../utils/afterPaint.ts](../utils/afterPaint.ts)), after the first frame the user sees; home's return-to-foreground handler does the same.
- `initNotificationHandlers()` returns a teardown; the caller must run it on unmount, or store subscriptions stack up and one change fans out N rebuilds.
- `withLock()` coalesces on the trailing edge: a request arriving mid-run queues exactly one re-run. Never make it drop-on-conflict.
- `rebuild()` replaces everything (`cancelAll()`, then `os.schedule()`) when the stored `SCHEDULE_FORMAT` stamp is stale, when `rebuild(true)` asks for it (`rebuildForNewDay()` does, so once a day), or, on Android, on the first rebuild of each JS process (`NotificationScheduler.replacedInProcess`): a force-stop removes every alarm but keeps expo's stored requests, which `getScheduled()` would still report, so a diff would never re-arm them, and a cold start always follows a force-stop. With notification permission gone it only cancels. Otherwise it calls `os.sync()`, which reads the pending notifications once and cancels the ids the plan lacks and those whose `data.contentHash` differs, and schedules only the new and the changed. A language, wording, trigger or payload change alters the hash, so it reschedules that reminder. `scheduleAll()` stays additive (`os.schedule()`).
- Only `rebuildForNewDay()` stamps `LAST_REBUILD_KEY`; a settings-driven `rebuild()` must not, or it suppresses that night's recovery run.
- Scheduling is capped and ordered by trigger time in `buildPlan()` (`planCap()`: `IOS_MAX - IOS_HEADROOM` (60) on iOS, `PENDING_LIMIT` (400, under Android's 500 alarms per app) elsewhere, one slot of it the end notice), every candidate names its channel and `os.schedule()` puts that `channelId` on the trigger, and a trigger outside its own window (a `followUp` one: outside the 720 minutes after it) is dropped.
- [notifications/](notifications/AGENTS.md) holds the planning contract: planners are pure over a `PlanInput` read once by `readPlanInput()`, only [notifications/os.ts](notifications/os.ts) calls expo-notifications for scheduling, and the facade keeps every exported name, the `NotificationScheduler` method set and the module-scope `defineTask` calls. Internal calls go through `NotificationScheduler.<method>` so the suites' spies keep working.
- Whether a reminder fires is `reminderFires()` from [../utils/skipRules.ts](../utils/skipRules.ts): ahead, from `HEADS_UP_MAX_MIN` (180) minutes before its own window's start through its end (a `followUp` reminder: in the `FOLLOW_UP_MAX_MIN` (720) minutes after the end; a `blockExit` reminder: after the window opens, up to its end, one trigger for each holy block that ends inside it), and not strictly inside a holy block. The plan and the mitzvah screen's next-reminder preview both reach it through `windowTriggers()` in [notifications/planners/mitzvot.ts](notifications/planners/mitzvot.ts), the one per-window rule, so the preview is `nextReminderAt()`, exported by the facade: the first trigger the scheduler would fire, across windows, never a copy of its filter. The horizon is `HORIZON_MAX_DAYS` (30) of the location's calendar dates (the first two stretch through any block that is reached or starts the next day, to the first weekday after it), planned in full and cut at the cap, furthest first; when the full plan does not fit, `planMitzvot()` keeps from the first day after the opening's holy-block stretch (`Horizon.thinFromIndex`, the third day at least) one trigger per window (a window with only `followUp` or `blockExit` triggers keeps its earliest) (see [notifications/AGENTS.md](notifications/AGENTS.md)). Mitzvah reminders are also planned for the two days before it (`PAST_WINDOW_DAYS`), for a window still open after midnight and a follow-up still due after a window that opened the day before yesterday, and a `multiDay` mitzvah's window `maxDays` back (its preview also looks `MULTI_DAY_LOOKAHEAD_DAYS` (45) days ahead); each step is the device-local midnight of that date, with zmanim at the location's noon, the mapping every day-level surface uses.
- [notificationResponseHandler.ts](notificationResponseHandler.ts) opens nothing while the app is quiet (onboarded and `isQuietAt()` now), drops a buffered cold-start tap then too, routes the body tap of a mitzvah reminder to the reader (`/siddur/[id]` with the notification's `date`) when `data.hasText` is true and to the detail screen (`/mitzvah/[id]`) otherwise or when the date cannot be recovered, the pre-block notice to home, a check-in reminder to `/checkin`, a taharah reminder to `/taharah`, a hilula notice to the page of the first tzaddik it names, `/hilula/[id]` (with `ids` when it names more than one), or to `/hilulot` for a notice scheduled before `ids` existed, a Rosh Chodesh notice to `/rosh-chodesh` and a weekly report notice to `/report` with its `week`, the end-of-reminders notice to home, and reloads into the update for an update notice through `reloadIntoUpdate()`, or opens home when that update, or a newer one, is already running. `MARK_DONE` is never blocked. expo-notifications hands a tap that launched a killed app to no listener added later, only to `getLastNotificationResponse()`: `openLaunchNotificationResponse()` reads it once the root layout's first screen is `(tabs)` (so the index redirect cannot replace the pushed route), skips a `MARK_DONE` (the headless task recorded it) and the response the listener already handled, and every handled response clears the stored one so a later launch never replays it. Suite: [__tests__/notificationResponseHandler.test.ts](__tests__/notificationResponseHandler.test.ts).
- `restoreBackup()` replaces, never merges. It suspends scheduling, drops `SCHEDULE_FORMAT_KEY` (a reload part-way, such as the RTL reload a restored language triggers, still rebuilds on the next foreground), writes each store's string and calls its `persist.rehydrate()` (so its own `migrate` and `merge` run, and the user store re-resolves its city), resets a store the file lacks and rehydrates it from nothing (the user store goes first, so the mitzvot store reads the file's `isOnboarded` and stamps only the default-on mitzvot its original defaults lack), calls `applyGenderDefaultsToNew()` (a default-on mitzvah the file's map lacks comes back on and stamped, and a men's one goes off again for a woman), calls `reconcileChokInstall()` (the restored mitzvot store may switch Chok LeYisrael on while this device holds no add-on) and `reconcileSelichotInstall()`, syncs the notification permission while still suspended, then lifts the suspension and rebuilds once. The taharah store is never touched. Last, unless the caller passes `{ reload: false }`, it calls `reloadIfScaleChanged()`: when the restored user store's `uiScale` is not the running `UI_SCALE` ([../theme/scale.ts](../theme/scale.ts), read once at launch), that calls `reloadApp()` from [appReload.ts](appReload.ts), so the app does not keep the old display size while Settings already shows the new step; a file at the running size reloads nothing. `reloadIfScaleChanged()` is exported for a caller that does work after the restore: the onboarding welcome step restores with `{ reload: false }`, asks for notification permission, rebuilds, and only then calls it, because a reload inside the restore would cut that short.
- `AppResetService` wraps its work in `setSchedulingSuspended(true)` so resetting the stores cannot re-arm a schedule from the restored defaults. It hydrates `useMitzvotStore` from nothing (`persist.clearStorage()` and `persist.rehydrate()`, right after the user store reset) instead of resetting it, so its default-on mitzvot are stamped with the reset, as on a fresh install. It resets `useTaharahStore` with the other stores and, after the main MMKV wipe, calls `clearTaharahStorage()`. It also resets `useChokStore`, cancels a running Chok LeYisrael download first and deletes the add-on's files after the main MMKV wipe, and does the same for `useSelichotStore`, cancelling a running Selichot download and deleting its files. - The taharah instance (`jew-365-taharah`) is encrypted with a 16-character key held in `expo-secure-store` under `taharah-mmkv-key`, read synchronously at module load and made on first use from `expo-crypto` random bytes. The key is always stored with `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`: it never travels in a backup or device transfer, yet the nightly rebuild and a lock-screen mark-done still read it on a locked phone. A key made just now clears the file it opens, since it cannot open anything older.
- When no key is available (web, or a keychain that cannot be read, such as a launch while the device is locked) the module opens a different, unencrypted file (`jew-365-taharah-unencrypted`). It must never open the encrypted file without its key: that decodes ciphertext as data and corrupts it. On iOS that file lives under `Library/Caches/mmkv` (MMKV's `path`, from `Paths.cache` of `expo-file-system`), never in MMKV's default `Documents/mmkv`, which rides the iCloud device backup; a purge of the caches loses only a fallback the encrypted file never relied on. On Android it stays in the default folder, which the backup whitelist of [../../scripts/withAndroidBackupRules.js](../../scripts/withAndroidBackupRules.js) leaves out.
- `clearTaharahStorage()` wipes the data and replaces the key in the secure store and in the running instance (`recrypt`). Deleting the key instead would leave this process writing under a key the next launch no longer finds. It never throws and restores the previous stored key if the new one cannot be applied. Run without a readable key, it wipes only the fallback file and sets `taharah:wipe-pending` in the plain store (after the reset's own wipe of it); the next launch that can read the key ignores the stored one, makes a new key and starts the encrypted file clean, then clears the flag.
- `ZmanimService.getZmanim()` must never throw. It returns `Zmanim | null`, where `null` means the sun neither rises nor sets that day; every caller must handle `null` instead of assuming a value. Depression-angle zmanim that have no solution fall back to their fixed-minute shita (alot 72 min, misheyakir 52 min before sunrise), and misheyakir is always kept inside `(alot, netz)`.
- A planner failure must cost only its own candidates (each mitzvah and day, each block, and the weekly report, taharah, hilula and Rosh Chodesh planners as a whole), so one failing mitzvah cannot empty the whole schedule: `cancelAll()` has already run.
- `skipOn` decisions come from `isSkippedAt()` in [../utils/skipRules.ts](../utils/skipRules.ts), evaluated at the computed window's `start`. Do not add a local copy of that predicate here, and do not judge the skip from `fromDate` — that instant carries the rebuild's clock time.
- `expo-file-system` (read by `SiddurService`, written by the add-on downloads) and `expo-keep-awake` (used by the reader) are pinned to the versions already linked into the shipped binary, and so is `expo-crypto` (15.0.9, the add-on's SHA-256 check). Raising any of them is a native change and needs a build; the add-on adds no native module (`fflate` is pure JS).
- `TaskManager.defineTask` calls stay at [NotificationScheduler.ts](NotificationScheduler.ts) module scope, and that module stays imported from the root [../../index.js](../../index.js) entry so both background tasks are defined during headless launches (killed-state `MARK_DONE` taps, background tasks). Route-only imports do not reach headless mode. Pinned by [backgroundTaskEntry.test.ts](__tests__/backgroundTaskEntry.test.ts), which also pins that `crashReporting` is imported before `expo-router/entry` and before `NotificationScheduler`. That module scope also calls `applyGenderDefaultsToNew()` from [../stores/taharahOptIn.ts](../stores/taharahOptIn.ts) once, after the user and mitzvot stores hydrate (synchronously, from MMKV), so a headless launch never plans a men's mitzvah the hydrate just added for a woman, and drops `SCHEDULE_FORMAT_KEY` when it returns any id (the `SCHEDULE_FORMAT` rule above); pinned by [NotificationScheduler.headless.test.ts](__tests__/NotificationScheduler.headless.test.ts).
