# AGENTS.md

## Purpose

- Own shared TypeScript domain types used across data, services, stores, and UI.

## Ownership

- [mitzvah.ts](mitzvah.ts) owns mitzvah, reminder, content block, and related domain shapes. `Weekday` is JS `getDay()` numbering (0 is Sunday). `CustomMitzvah.schedules` is a list of `ScheduleEntry`s (`from`, a `YYYY-MM-DD` location day, and a `CustomSchedule`: `weekdays` with `days`, `range` with `start` and `end`, or `streak` with `start` and a count of `days`), sorted by `from`; `CustomMitzvah.activeDays` is the legacy weekday list (absent means every day) that a mitzvah without `schedules` is read by, and a save drops it. `CustomMitzvah` has no `category`: [../data/customMitzvotAdapter.ts](../data/customMitzvotAdapter.ts) derives it from the hours, and a stored mitzvah that still carries the key keeps loading with it ignored. A `ContentBlock` is `text`, `blessing`, `link` or `siddur` (a bundled siddur text by its `SiddurTextId`); the reader's custom text and the notification body read only `text` and `blessing`. A `Reminder`'s `ReminderAnchor` is `start` or `end` (`offsetMin` is minutes from that edge of the window) or `clock` (`offsetMin` is minutes after midnight, 0-1439, on the location's clock); every mitzvah, registry and custom alike, may store any of the three. `followUp` (`offsetMin` is minutes after the window's end, 1-720) fires only while the day is not marked; only the custom mitzvah editors offer it. `blockExit` (`offsetMin` is minutes, 0-720, after the exit of each holy block that ends inside the window) is offered only for a mitzvah with `multiDay`. `Mitzvah.multiDay` (`{ maxDays }`) marks a registry mitzvah whose window outlasts a day: the engine looks back up to `maxDays` for one still open. `Mitzvah.group` is the mitzvot library section, a `LibraryGroup` (`prayers`, `daily`, `weekly`, `seasonal`, `other`, `mine`): required on every registry entry, and `mine` only from the custom adapter; `category` stays the time-of-day class. `Mitzvah.bodyParams(ctx)` returns the `BodyParams` (strings and numbers) the planner fills into a reminder's `%{key}` placeholders for that window's day, and `Mitzvah.bodyKey` names the i18n key of the body line built from them (English always, Hebrew when the reminder's text holds no placeholder and is the registry's own label or variant or the mitzvah's name, never for a label the user typed); both optional, registry only.
- [zmanim.ts](zmanim.ts) owns zmanim-related shared types. `Location.cityId` is the stable id of the [../data/cities.ts](../data/cities.ts) entry a location came from; it is optional because a GPS fix far from every city has none and a snapshot saved before the field existed lacks it. [../stores/useUserStore.ts](../stores/useUserStore.ts) re-resolves a saved location by it on every hydrate.
- [siddur.ts](siddur.ts) owns siddur text, section, segment, run, condition, day-flag and passage-label shapes (`optional` and `minyan`; a label may carry `alone`, which opens its fold by default when praying alone, or `marriedOnly`, which hides its passage from a single reader, or `voice` (a `SiddurVoice`, `male` or `female`), which shows its passage unfolded only to that voice, hides it from the other and keeps it folded for a reader with no voice, or `foldsFor` (a `SiddurVoice`), which keeps its passage folded only for that voice and reads it open for the other voice and for a reader with no voice), a section's optional `chapter` (the picker entry it opens), its optional `headings` (`SectionHeading`s the reader draws above its card: level 1 opens a book of a text, level 2 a part of it; only Tehillim carries them), the `SegmentBlock` the reader renders, and the text ids: `MitzvahTextId` (a mitzvah's id), `StandaloneTextId` (a text with no mitzvah) and `SiddurGroup` (how the catalog groups the latter: `meals`, `general`, `occasions`, each also an icon name in [../components/MitzvahIcon.tsx](../components/MitzvahIcon.tsx); the catalog's now and prayers cards are not groups). The generated text assets follow the text ids, so a new or renamed id here needs `pnpm siddur:build`; a group change does not. A `Run`'s style is `b` (bold), `n` (a note, drawn small) or `t` (a targum line, drawn smaller in `textSub`). A `Run`'s `voice` (`VoiceAudience[]`: `male`, `female`, `unset`) lists who reads it, `unset` being a reader with no voice, who reads the text as printed; a run without one is read by everyone. A `Run`'s `marriedOnly: true` marks a voiced wording only a married reader, or one who has not answered, reads. `SiddurText.nusach` is optional, because a Chok LeYisrael text and a text shared by every nusach (Tikkun HaKlali, Tehillim) have none, and its optional `dedication` is the line the reader shows above the sources. `SelichotDayFlag` and `SelichotTeshuvaFlag` name the Ashkenazi selichot days. `KiddushLevanaFlag` (`kiddushLevanaAshkenaz`, `kiddushLevanaSefard`, `kiddushLevanaEdotHamizrach`, `kiddushLevanaChabad`) names the nights each nusach's Kiddush Levana period holds. `Place.location` is set by `siddurPlace()` and read only by those flags. It also owns `SiddurChapterTitle` (`he`, `en`, optional `voices` and `marriedOnly`) and `SiddurChapterIndex`, the shape of the generated chapter index. A segment's optional `key` (stable across days and rebuilds, written by the build, Chok's from `chokText()`, absent on a custom text) names it for the reader's bookmarks, and `SiddurPlace`, `SiddurBookmark` and `SiddurLastPosition` are the shapes of [../stores/useSiddurBookmarksStore.ts](../stores/useSiddurBookmarksStore.ts).
- [addon.ts](addon.ts) owns the shapes every downloadable add-on shares: `AddonManifest` (the published `manifest.json`: format, version, the total `gzipBytes`, and a path, SHA-256 and size per key under `gz` for its gzip; a key is a parasha for Chok LeYisrael and a nusach for Selichot) and `AddonManifestFile`, `AddonInstall` (what the device holds: version, bytes, install time and the file name of each installed key), `AddonFailureReason` (`offline`, `unavailable`, `integrity`, `space`, `storage`) and `AddonDownload` (`idle`, `downloading` with its progress, `failed` with a reason).
- [chok.ts](chok.ts) owns the Chok LeYisrael shapes: `ChokSlot` (`sun` to `thu`, `thuNight`, `fri`), `ChokSectionKind`, `HaftarahVariant` (`sephardi`, `ashkenazi`), `ChokDoubleChoice` (`first`, `second`, `both`), `ChokThuNightDay` (`thu`, `fri`: the day a mark made in the reader's ליל שישי fills), `ChokSection` (kind, the heading as the source prints it, an optional haftarah variant, `SiddurSegment`s) and `ChokAsset`, the JSON of one generated parasha (`parasha` by its hebcal name, `credit`, `dedication`, `slots`). A change to `ChokAsset` or `ChokSection` changes the output of [../../scripts/chok/AGENTS.md](../../scripts/chok/AGENTS.md) and needs a rebuild. Its download shapes are the Chok names of the [addon.ts](addon.ts) shapes: `ChokManifestFile`, `ChokInstall` (what the device holds: `.json.gz` names, or `.json` for an install made before the compressed download), `ChokFailureReason` and `ChokDownload`, and `ChokManifest`, the `AddonManifest` with the credit, the license and, optional because the app reads only `gz`, the plain JSON under `files` with its total `bytes`.

- [taharah.ts](taharah.ts) owns the niddah-cycle shapes: `Onah` (a hebcal absolute day number plus night or day), `TaharahRules`, `TaharahSettings` and the preset ids, the raw `TaharahEvent` union, and the derived `CycleState`, `PerishaOnah`, `KavuaHint` and `TaharahTask`. The engine that produces the derived shapes is [../utils/taharah/](../utils/taharah/).

## Local Contracts

- Type changes must be coordinated with all consumers in [../data/AGENTS.md](../data/AGENTS.md), [../services/AGENTS.md](../services/AGENTS.md), [../stores/AGENTS.md](../stores/AGENTS.md), and [../app/AGENTS.md](../app/AGENTS.md).
- Keep optional fields backward-compatible when persisted data or custom mitzvot may already exist.
- In [taharah.ts](taharah.ts) only `TaharahEvent` and the settings are persisted input. `CycleState`, `PerishaOnah`, `KavuaHint` and `TaharahTask` are derived by replay and never stored, so a new event field is optional and a rule change needs no migration.

## Work Guidance

- Favor explicit domain names over broad generic shapes.
- Avoid widening types just to suppress local errors; fix the caller or model the state precisely.

## Verification

- Run `pnpm typecheck` after any type change.
- Run affected domain tests when a type change changes runtime behavior.
