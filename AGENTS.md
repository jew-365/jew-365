## Commands

```bash
pnpm start                         # expo start / Metro
pnpm start:dev                     # expo start --dev-client
pnpm prebuild:clean                # regenerate native folders from app.json (run after app.json identity changes)
pnpm android                       # expo run:android
pnpm android:device                # expo run:android --device
pnpm ios                           # expo run:ios
pnpm web                           # frees port 8081, then expo start --web
pnpm test                          # jest
pnpm test:tz                       # full suite across UTC, Jerusalem, LA and Kiritimati
pnpm test:tz -- path/file.test.ts  # one file across the same four zones
pnpm test -- path/to/file.test.ts  # single Jest file
pnpm test -t "name fragment"       # Jest test-name filter; no --, which pnpm passes on and Jest then reads -t as a path
pnpm typecheck                     # tsc --noEmit
pnpm lint                          # eslint (eslint-config-expo + prettier config), zero warnings expected
pnpm format                        # prettier --write; format:check is the read-only form
pnpm check:dox                     # AGENTS.md links, section order and Child DOX Index
pnpm siddur:build                  # rebuild the bundled nusach texts and docs/selichot, the downloadable Selichot add-on, from pinned Sefaria and Wikisource sources
pnpm chok:build                    # rebuild docs/chok, the downloadable Chok LeYisrael add-on, from scripts/chok/source
pnpm guide:build                   # rebuild docs/guide, the web copy of the user guide in src/data/guide.ts
pnpm logo:build                    # redraw the logo SVGs and export every PNG in assets/ and assets/preview/ and src/components/logo.generated.ts (needs Chrome or Edge)
pnpm doctor                        # expo-doctor
pnpm build:android:production:aab  # EAS production AAB for the Play Store
pnpm build:android:production:apk  # EAS production APK for direct install
pnpm build:ios:production          # EAS production build for App Store / TestFlight
pnpm submit:ios                    # upload the latest iOS build to App Store Connect
pnpm build:android:preview:apk     # EAS internal APK of the preview variant "Jew 365 P", installs beside production
pnpm build:ios:preview             # EAS internal iOS build of the preview variant for a registered iPhone
pnpm update:production --message "…"   # numbered EAS update to production — reaches installed users
pnpm update:preview --message "…"      # numbered EAS update to the preview channel — reaches only the preview app
pnpm build:android:development     # EAS development client APK
pnpm update:development --message "…"  # numbered EAS update to the development channel
```

Each build command names its platform, its profile and, on Android, its artifact: an AAB is what the Play Store takes, an APK installs directly on a phone. A build is a new binary and is needed only for a native change; an update replaces the JavaScript bundle of every installed build on its channel (production or preview) with the same `version`.

`pnpm web` calls [scripts/free-port.js](scripts/free-port.js) (cross-platform) and may kill a listener on port 8081. Use a dev client/native build when verifying `react-native-mmkv`, background tasks, or notifications.

[.github/workflows/ci.yml](.github/workflows/ci.yml) runs `typecheck`, `lint`, `check:dox` and `test:tz` on every push to `main` and every pull request. The husky pre-commit hook runs lint-staged (`eslint --fix` and `prettier --write` on the staged files), so a commit never carries a lint error. ESLint's config is [eslint.config.js](eslint.config.js); test and mock files may keep `jest.mock` above their imports and `require` inside factories.

Jest ([package.json](package.json)), Metro ([metro.config.js](metro.config.js)) and `check:dox` all ignore [.claude/](.claude), where agent sessions keep full worktree copies of the repo. Without that, a worktree's tests run twice against the wrong module paths, its AGENTS.md files fail the DOX check, and a `pnpm install` inside it crashes Metro's file watcher.

## Release and Updates

Two different mechanisms ship this app, and the choice is not stylistic: one reaches everybody within a minute, the other reaches nobody until users install a new binary.

- **Anything Metro bundles** — TypeScript, JSX, i18n strings, and bundled assets (fonts and the siddur texts included) — ships as an over-the-air update: `pnpm update:preview`, or `pnpm update:production` for real users.
- The Chok LeYisrael text is neither bundled nor shipped by an update: `pnpm chok:build` writes [docs/chok/](docs/chok), a push to `main` publishes it on GitHub Pages, and the app downloads it when the user asks ([src/services/ChokContentService.ts](src/services/ChokContentService.ts)); a new content version reaches installs as an update offer on the mitzvah screen, while the code that reads it ships over the air like any other code. A bundle whose reader needs a new manifest field (`gz` and `gzipBytes` today) refuses a manifest without it, so push the regenerated [docs/chok/](docs/chok) to `main` and confirm it is live on Pages before publishing that update.
- The Selichot text is not bundled either: `pnpm siddur:build` writes one gzip per nusach and a manifest to [docs/selichot/](docs/selichot), a push to `main` publishes it, and the app downloads the user's nusach on request ([src/services/SelichotContentService.ts](src/services/SelichotContentService.ts)). Push it and confirm `https://jew-365.github.io/jew-365/selichot/manifest.json` is live before publishing the update that drops the bundled text; a binary keeps the assets it was built with, so the app shrinks only with the next build.
- **Anything native** — a dependency with native code, an Android permission, a config plugin under [scripts/](scripts), or an identity field in [app.json](app.json) — needs a build: `pnpm build:android:production:aab` for the store (`:apk` for a direct install, `pnpm build:ios:production` for iOS). EAS builds it on its own servers and runs prebuild there, which is why the native folders stay gitignored and are safe to delete locally.
- A native module that `expo` already links transitively (`expo-file-system`, `expo-keep-awake`) may be added as a direct dependency over OTA only at the exact version the shipped binary carries. Check the committed lockfile before raising one.
- React Navigation is pinned by `pnpm.overrides` in [package.json](package.json) to one copy of each package, the copies expo-router 6.0.24 resolves to as well: the 2026-07-07 set that carries the bottom-tabs detach fix, `@react-navigation/bottom-tabs` 7.18.8, `elements` 2.9.30, `native` 7.3.8, `core` 7.21.5 and `routers` 7.6.0, with `native-stack` held at 7.14.12 so the stack's calls into `react-native-screens` stay the ones the shipped binary already runs. They are pure JS and ship as an update only while the lockfile diff leaves every native package alone (`react-native-screens` 4.16.0, `react-native-safe-area-context` 5.6.2). Raise the overrides together, then `pnpm why @react-navigation/bottom-tabs` must list one version; [src/app/__tests__/tabsLayout.render.test.tsx](src/app/__tests__/tabsLayout.render.test.tsx) fails on a second copy or on a bottom-tabs older than 7.18.8.
- The first build of `com.jew365.app` carries every native module in [package.json](package.json), the taharah modules (`expo-secure-store`, `expo-crypto`, `expo-local-authentication`), `@sentry/react-native`, `expo-background-task` and `expo-sharing` among them, the local `power-settings` module ([modules/](modules)) with the `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` permission, and the Android Auto Backup whitelist (`allowBackup: true` plus [scripts/withAndroidBackupRules.js](scripts/withAndroidBackupRules.js)). Until that build is installed somewhere, an update reaches nobody: the project has no other build.
- Crash reporting is Sentry ([src/services/crashReporting.native.ts](src/services/crashReporting.native.ts)). It is native, so it ships only in a build. It stays off without `EXPO_PUBLIC_SENTRY_DSN`, which Metro inlines at bundle time (see [.env.example](.env.example)); `SENTRY_AUTH_TOKEN`, which uploads source maps during an EAS build, is an EAS secret, never a file. `pnpm.onlyBuiltDependencies` in [package.json](package.json) allows the `postinstall` of `@sentry/cli`, which pnpm 10 would otherwise skip, and EAS needs it too for the `sentry-cli` binary the Sentry Expo plugin runs during a build. `@sentry/cli` is also a direct dev dependency at the exact version `@sentry/react-native` depends on (2.55.0 for 7.2.0): the SDK's iOS "Upload Debug Symbols to Sentry" build phase calls `require.resolve('@sentry/cli/package.json')` from the `ios` folder under `set -e`, before it reads `SENTRY_DISABLE_AUTO_UPLOAD`, and pnpm does not hoist a transitive package there, so iOS build `1b4f562b` failed until it was added. Raise both together. The `organization` and `project` of the `@sentry/react-native/expo` entry in [app.json](app.json) are placeholders until the user fills them. Source-map upload is disabled in every build profile of [eas.json](eas.json) (`SENTRY_DISABLE_AUTO_UPLOAD`) until a Sentry account exists (`SENTRY_AUTH_TOKEN` as an EAS secret and the real `organization` / `project` in [app.json](app.json)); removing the two production `env` lines turns the upload back on.

An update carries no native code, so shipping a native change as an update produces a bundle that calls into something the installed binary does not have. Prefer an update; reach for a build only when the change is actually native.

### Every update is numbered

Settings shows `<version>-<n>`: `n` counts the updates published on that channel for that `version`, and a build shows `-0`. The user asked for it on 2026-10-08 so the phone shows which update it runs.

- `pnpm update:*` runs [scripts/publish-update.js](scripts/publish-update.js), which takes the next `n` from EAS and publishes with it. Never publish with `npx eas-cli update` directly: the update would carry no number and the next one would repeat a number.
- A production update also needs its user guide entry: [scripts/publish-update.js](scripts/publish-update.js) refuses `pnpm update:production` unless `WHATS_NEW` in [src/data/guide.ts](src/data/guide.ts) has an entry labelled with the `<version>-<n>` it is about to publish, and names the missing label. `--skip-whats-new` passes the check only with a `--message` that starts with `Rollback to `, for republishing a known-good bundle.
- `n` starts each EAS message (`1.0.20-1: …`), so the dashboard and `eas update:list` show the same label as the phone.
- A ready-update banner floats over every screen once an update is downloaded (`UpdateBanner` in [src/components/UpdateBanner.tsx](src/components/UpdateBanner.tsx), mounted by the root layout; the user's call, 2026-10-10). The app checks for one at launch (expo-updates) and on every return to the foreground. The hourly background task (`jew-365-daily-rebuild`) checks as well and, outside development, holy blocks, the quiet hours and a switched-off notifications setting, presents one `update:<update id>` notification per downloaded update (`notifyIfUpdateReady()` in [src/services/NotificationScheduler.ts](src/services/NotificationScheduler.ts)); a tap reloads into the update, or opens home when it, or a newer one, is already running. Background fetch runs when the OS allows, so the notice can trail the publish by an hour or more on Android and by longer on iOS.
- Launches, failed launches and unique users of an update: `npx eas-cli update:insights <group-id>`, or the update's Insights tab on expo.dev.
- Roll back by republishing the last good group, which keeps its number on the phone: `npx eas-cli update:republish --group <group-id> --message "Rollback to <version>-<n>" --non-interactive`. `npx eas-cli update:roll-back-to-embedded` returns every install to its build's bundle (`-0`). Rolling back past the update that stores Chok compressed leaves a `.json.gz` install unreadable to the older bundle; the reader shows its retry state until the user deletes and downloads the add-on again.

### Never raise `version` for a JS change

[app.json](app.json) sets `runtimeVersion` to the `appVersion` policy, so an update only reaches installs whose build carried the **same** `version`. Raising `version` therefore cuts every existing install off from over-the-air updates until a new build ships **and** each user installs it — the previous version keeps running the last bundle published under it, and nothing warns that the two diverged.

Bump `version` only in the change that also produces a native build, and update [package.json](package.json) in the same edit: nothing enforces that the two agree, and they were already one release apart at 1.0.12 / 1.0.13.

### Version codes are remote

[eas.json](eas.json) sets `appVersionSource` to `remote`, so EAS owns the Android `versionCode` and the iOS `buildNumber`, and every profile with `autoIncrement` raises them itself. Never hand-edit a version code or build number, and never add one to [app.json](app.json).

### The preview variant

`pnpm build:android:preview:apk` builds a second app that installs beside production (the owner's call, 2026-10-25): "Jew 365 P" in English and `יהודי 365 P` in Hebrew ([locales/preview/](locales/preview)), application id and iOS bundle id `com.jew365.app.preview`, scheme `jew365preview`, and today's icon in red shades instead of blue ([assets/preview/](assets/preview), drawn by `pnpm logo:build`).

- [app.config.js](app.config.js) is the only switch. `APP_VARIANT=preview`, set in the `env` of the `preview`, `preview-device` and `preview-ios` profiles of [eas.json](eas.json), returns a copy of the [app.json](app.json) config with the name, scheme, package, bundle id, the iOS `CFBundleDisplayName` (`יהודי 365 P`, so a language without a localized name still shows the preview's), icon, adaptive foreground, the two splash images, the notification colour (the red ink of the mark) and the native strings replaced. Every other value stays production's: slug, owner, project id, update URL, `version` and the `appVersion` runtime policy, plugins, permissions. Without the variable, or with any other value, it returns the config it was given, so [app.json](app.json) stays the production identity and every test and script that reads it keeps working. [scripts/__tests__/appConfig.test.js](scripts/__tests__/appConfig.test.js) pins both sides. Never change a production identity field through this file: a different package or bundle id is a different app that no update reaches.
- The preview app has its own data, settings, completions and notifications, as a separate application id has its own sandbox: with both installed and reminders on, both remind. It runs the `preview` channel, so `pnpm update:preview` reaches it and never a production install. `eas update` does not apply the `env` of a build profile, so [scripts/publish-update.js](scripts/publish-update.js) puts `APP_VARIANT=preview` in the environment of an update published to the `preview` channel; without it the update's manifest would carry production's name, scheme and icon paths into the preview app.
- The first build of each platform needs credentials for the new id. On Android, `eas build --non-interactive` generates a random keystore and stores it on EAS (an interactive run asks first); on iOS, the certificate and provisioning profile need the owner's Apple sign-in. Production's credentials are never touched.
- iOS: the profile is `preview-ios` (internal distribution, a real device, not the simulator), built by `pnpm build:ios:preview` once the iPhone is registered with `npx eas-cli device:create`, the owner's step. No Apple step has been taken; [not-close.md](not-close.md) tracks it.

### Store submission is manual

`submit.production` in [eas.json](eas.json) is empty, so no submission runs unattended.

Android has a Google Play service account (`play-cli@jew365-store.iam.gserviceaccount.com`, no production release permission) for [scripts/store/play.mjs](scripts/store/play.mjs), but `eas submit` is not configured with it, so uploading a production build to the Play Console stays a human step, or a `play.mjs upload` the owner approves.

iOS has no stored credentials either, but `pnpm submit:ios` still works — `eas submit --latest` prompts for the Apple account and target app each run. Do not hardcode an Apple ID, team ID or ASC app ID into [eas.json](eas.json) unless the user supplies real values.

Store copy lives in [release/](release).

### Project records

Three root files say what is open, what is in production and where the project stands. Every agent keeps them current in the same change as the work, never in a later pass:

- [not-close.md](not-close.md) holds every item until it is in production: tasks, bugs, open questions and other open items. New work goes there, never into a separate tasks, bugs or questions file. When an item's work is done and its expected result checked, the item stays and gains a Done line (the date and how it was verified) and a Status line (Version · Committed · Pushed · Live · Channel). Each later step updates that Status line in the same pass: a commit fills Committed with the hash and subject, a push sets Pushed, and a release outside production (a `preview` update, the preview app, Play closed testing, TestFlight, a direct APK) sets Live and Channel. Work done without ever being an item (a fix found and made in one pass) becomes an item with those lines.
- Production in this project, per release path: an over-the-air update on the `production` channel; a native build released on Google Play's production track, or on the App Store after the owner's Release (never closed testing, TestFlight or a direct APK); [docs/](docs) content once `main` on GitHub holds it and Pages serves it. An item that ships through several paths waits for each, and its Live says which path is not in production yet.
- An item moves to [action-log.md](action-log.md) only when it is in production. The agent that holds the proof moves it in the same pass, without asking, and reports it: the item has a Done line, `origin` holds its commits, and a production release of the item's own release path was built from a commit that contains them (`git merge-base --is-ancestor`; an update's commit is `gitCommitHash` in `npx eas-cli update:view <group> --json`; an over-the-air update does not carry a native change). Work that never reaches users (tooling, tests, internal docs, the preview app) moves with the next production release after it is pushed. Short of that proof, propose the move and wait. A production rollback brings back the items only that release carried. A check that could not run yet stays in not-close.md as an open item.
- [state.md](state.md) changes whenever the release or store status changes: a publish or rollback, a build, an upload, a review result, a tester or store milestone, a version raise. Its facts are read from EAS, the consoles or [release/RELEASE_LOG.md](release/RELEASE_LOG.md), never assumed, and it carries the date they were read.
- A value no record proves is written `unknown`, never guessed; a tag proves a version, not a deploy. Apart from the move to production, an item never leaves not-close.md without the owner's word; an item the owner drops moves to [action-log.md](action-log.md) at once as a `Declined:` entry with the owner's words and date.

## Architecture Rules

- TypeScript is strict. The `@/*` alias maps to `src/*` in both [tsconfig.json](tsconfig.json) and [babel.config.js](babel.config.js); update both if aliases change.
- Keep app logic in services/utils/stores where possible. Components and routes should mostly compose state, services, and UI.
- Calendar and zmanim logic runs through `kosher-zmanim`, `@hebcal/core` and `luxon`.
- Do not commit generated native folders unless the user explicitly asks for native project changes. the root `/android/` and `/ios/` are gitignored (a nested `android/` folder such as [modules/power-settings/android/](modules/power-settings/android) is tracked) and normally generated by Expo prebuild/run.
- Treat an existing `ios/`/`android/` folder as disposable cache, never as state. Expo skips prebuild when the folder exists, so a stale one silently builds the wrong `applicationId`, scheme, update URL and app name. After any change to identity fields in [app.json](app.json), run `pnpm prebuild:clean`.
- Hebrew is primary. Do not replace Hebrew source strings with English. User-facing copy should usually go through i18n when it is normal UI text.

Default enabled mitzvot are the registered ids of `DEFAULT_ON_MITZVOT` in [useMitzvotStore.ts](src/stores/useMitzvotStore.ts): `tefillin`, `krias_shma_shacharit`, `shacharit`, `mincha`, `maariv`, `krias_shma_al_hamita`, and, once each is in the registry, `kiddush_levana`, `selichot`, `chanukah_candles` and `ushpizin` (the user's call, 2026-10-24). An install receives a newly default-on mitzvah switched on with `enabledAt` stamped at the hydrate that adds it, so its earlier days never count as misses, except a `multiDay` window still open at the hydrate, which is judged by its own end (an onboarded install that never saved the store starts from the old five, `tefillin` through `maariv`, so it is covered too; a fresh install, not yet onboarded, has every default-on id stamped with its first launch, so a new user is never asked about or judged on days before the install); for a woman one in `MENS_MITZVOT` ([taharahOptIn.ts](src/stores/taharahOptIn.ts): `tefillin`, `kiddush_levana`) stays off (`applyGenderDefaultsToNew()`). `tzitzit` was removed on 2026-10-11 (the user's call): `RETIRED_MITZVOT` in [useMitzvotStore.ts](src/stores/useMitzvotStore.ts) prunes it from every persisted map on hydrate, its old completion rows stay in storage and still count for the streak, and the tallit katan blessing survives, unfolded under a line that names who says it, at the top of the `tefillin` siddur text and at the start of Shacharit's tallit and tefillin section.

Chok LeYisrael (`chok_leyisrael`, `CHOK_LEYISRAEL` in [src/data/mitzvot.ts](src/data/mitzvot.ts), the user's call on 2026-10-11) is a `learning` mitzvah, off by default and always last in `MITZVOT`. Its text is an optional add-on downloaded inside the app (the user's call, 2026-10-23): until it is installed (`hasChokContent()` in [src/data/chok.ts](src/data/chok.ts), the install held by [src/stores/useChokStore.ts](src/stores/useChokStore.ts)) its window is `null`, so nothing schedules, shows on home or judges it, and the library, the More tab and its own screen offer the download. Its window is the reader's learning day: from alot to the next day's alot, or to candle lighting when a holy block opens that evening, and `null` on Shabbat, Yom Tov and the Friday of a Vezot Haberakhah week. Its "פתח נוסח", on the mitzvah screen and on home's card, opens the reader with no date, on the portion of the moment, so on Thursday night it opens ליל שישי. Its one default reminder is a `clock` reminder at 09:00 on the location's clock (the user's call, 2026-10-23), editable in the reminder editor; it fires on every learning day, Fridays and erev Yom Tov included, since candle lighting is always later. ליל שישי has its own "סיימתי" (the user's call, 2026-10-25), filed under Thursday or Friday by `useUserStore.chokThuNightDay`, which the reader asks once and Settings → Prayer offers as chips; filed under Friday it marks Friday ahead of its window, so Friday's reminders drop, and in a Vezot Haberakhah week it files under Thursday. An earlier day of the current week is marked late from the reader's make-up folds; a Yom Tov day can be marked too, but has no window, so it reaches only the streak.

Each `Mitzvah` has:

- `timeType`: `fixed-moment`, `range-within-day`, `sunset-trigger`, `date-range`, `monthly-window`, or `annual-seasonal`.
- `category`: the time-of-day, weekly, seasonal or learning class: the custom form's category pill, the library row's caption and the mitzvah screen's cycle label.
- `group`: the library section (`LibraryGroup`): `prayers`, `daily`, `weekly`, `seasonal`, `other`, or `mine`, which only the custom adapter sets; required on every registry entry, in the order of `LIBRARY_GROUPS` in [src/data/mitzvot.ts](src/data/mitzvot.ts).
- `computeWindow(ctx)`: returns `{ start, end }` or `null`.
- `defaultReminders`: reminder definitions with `anchor`, `offsetMin`, `label`, optional `bodyVariants`, `includeContentInBody`, and `skipIfDone`. `anchor` is `start` or `end` (`offsetMin` is minutes from that edge of the window) or `clock` (`offsetMin` is minutes after midnight, 0-1439, on the location's clock: the reminder fires at the first such wall-clock time inside the window, else the first one at or after `HEADS_UP_MAX_MIN` (180) minutes before the window's start). Every mitzvah, registry and custom alike, may use all three anchors and any number of reminders (the user's call, 2026-10-24). A trigger fires from `HEADS_UP_MAX_MIN` (180) minutes before the window's start (a heads-up; a `start` offset may be negative down to -180) through the window's end, never strictly inside a holy block: `reminderFires()` in [src/utils/skipRules.ts](src/utils/skipRules.ts) is the one rule, shared by the planner, `nextReminderAt()` and the reminder editor. A fourth anchor, `followUp` (the user's call, 2026-10-24), counts `offsetMin` (1 to `FOLLOW_UP_MAX_MIN`, 720) minutes after the window's end and goes out only while that window's day is neither done nor skipped: the plan drops a marked day, a later mark cancels it through `cancelForMitzvah()`, and `skipsIfDone()` in [src/utils/skipRules.ts](src/utils/skipRules.ts) sets its `skipIfDone`. `reminderFires()` accepts it in `(end, end + 720 min]`, the only trigger after a window, still never strictly inside a holy block. Only the custom mitzvah editors offer it; its default label is `reminder.followUp.label`. A fifth anchor, `blockExit`, counts `offsetMin` (0 to 720) minutes after the exit of each holy block that ends strictly inside the window (`blockExitsWithin()` in [src/utils/skipRules.ts](src/utils/skipRules.ts)), one trigger per exit; `reminderFires()` accepts it in `(start, end]`, and the reminder editor offers it only for a `multiDay` mitzvah.
- `skipOn`: skip contexts. Every surface consumes `shabbat`, `yomtov` and `cholHamoed` through `isSkippedAt()`. `cholHamoed` follows the tefillin minhag in `keepsCholHamoed()`: skipped in Israel and for every nusach but Ashkenaz abroad.
- `nuschaotSupported`: supported nusach IDs.
- optional `contentBlocks`: text/blessing/link blocks shown on detail screens and optionally included in notifications.
- optional `bodyParams(ctx)` and `bodyKey`: `bodyParams` returns the `BodyParams` (a flat record; a value may be a `{ he, en }` pair, read in the body's language) that `planMitzvot()` fills into the `%{key}` placeholders of a reminder's Hebrew variant or label for that window's day (`interpolate()` in [src/i18n/index.ts](src/i18n/index.ts)), or `null`; `bodyKey` is the i18n key of the body line, read with `name` and the same values instead of `notifications.timeFor`: always in English, and in Hebrew when the reminder's text holds no placeholder and is the registry's own wording: a label or variant of the mitzvah's `defaultReminders` (an edited default reminder keeps its label but no variants) or the mitzvah's name, which the reminder editor saves for an empty label. A label the user typed is sent as typed, its `%{key}` placeholders filled (`bodyForReminder()` in [src/services/notifications/planners/mitzvot.ts](src/services/notifications/planners/mitzvot.ts)). The Chanukah candles name the night (`n`, 1-8) this way, and Ushpizin the night's guest (`guest`, a `{ he, en }` pair).
- optional `multiDay: { maxDays }`: the window outlasts a day (Kiddush Levana, 16), keyed on its first day. `appDayWindow()`, `currentOrNextWindow()` and `planMitzvot()` look back up to `maxDays` for one still open, so home shows it every night and day of its period; `currentOrNextWindow()` and `nextReminderAt()` look ahead `MULTI_DAY_LOOKAHEAD_DAYS` (45) days for the next one. `judgeDay()` judges it by its own end, and a mitzvah switched on before that end is judged on it; while it is open it does not hold its day in the streak, which `computeStreak()` judges by the day's other items. `waitsInCheckIn()` keeps one that ends after a holy block out of that block's check-in. Home leaves it out on an app day after the one it was marked on.

When adding or changing a mitzvah, update `MITZVOT`, any relevant i18n/UI labels, and tests under [src/data/__tests__/](src/data/__tests__), [src/services/__tests__/](src/services/__tests__), and any affected route/component tests.

Custom mitzvot live in `useCustomMitzvotStore` and are adapted through [customMitzvotAdapter.ts](src/data/customMitzvotAdapter.ts). Custom IDs are generated as `custom_<timestamp>_<suffix>`. Use `getAllMitzvot(nusach?)` or `findAnyMitzvah()` when a screen/service must include custom mitzvot. Passing the nusach applies `nuschaotSupported` filtering; every surface that lists mitzvot must filter the same way. A custom mitzvah applies on the days its `schedules` allow (`appliesOn()` in [src/utils/customMitzvah.ts](src/utils/customMitzvah.ts): on a location day the entry in force is the last whose `from` is on or before it; `weekdays` applies on its weekdays, `range` from `start` through `end`, `streak` for `days` days from `start`; a mitzvah without `schedules` reads its legacy `activeDays` as one weekdays entry from the beginning of time, so there is no migration). Hours that end at or before alot of the date asked for are placed on the next date, so a window wholly in the night belongs to the evening before on every surface and its weekday, range or streak day is that evening; hours that reach past alot keep their own date ([customMitzvotAdapter.ts](src/data/customMitzvotAdapter.ts)). A save that changes the schedule appends an entry from today's app day, so earlier days keep the schedule they had, and an ended range or streak is switched off on every foreground by `reconcileEndedCustomMitzvot()` ([src/stores/customMitzvahLifecycle.ts](src/stores/customMitzvahLifecycle.ts)), its completions kept. It takes its category from its hours, and may carry a `siddur` content block that opens a bundled text in the reader but never joins its custom text or its notification body.

## Zmanim and Calendar

- `ZmanimService.getZmanim(date, location)` wraps `kosher-zmanim` `ComplexZmanimCalendar`, resolves the calendar day in the location's timezone, caches up to 90 entries, and returns cloned `Date` objects. It returns `null` (never throws) when the sun neither rises nor sets. It replaces kosher-zmanim's antimeridian adjustment with `antimeridianAdjustment()`, because kosher-zmanim 0.9.0 reads a DST zone's raw offset with the wrong sign and gave Sydney and New Zealand the next day's zmanim.
- Sunrise/sunset use sea-level getters. `tzeitHakochavim` uses `getTzaisGeonim7Point083Degrees()`.
- Candle lighting uses the same sea-level sunset basis, via `candleLightingMinutes(location)`: 40 minutes in Jerusalem (local minhag), 18 elsewhere in Israel, 20 outside Israel, or `location.candleLightingMinutes` when set. It opens once per holy block, on its erev; havdalah once, at the block's exit, plus the Sunday night after a Tisha B'Av fast that falls on Sunday, as it is or deferred from Shabbat, at tzeit itself.
- Shabbat and Yom Tov leave `HOLY_BLOCK_EXIT_MIN` (10) minutes after tzeit, the user's call on 2026-10-10: `holyBlockExit(zmanim)` in [src/services/ZmanimService.ts](src/services/ZmanimService.ts) is the one place the margin lives. It sets a block's `end` (so the Shabbat screen, the pre-block notice and the check-in nudges show and use the exit), and `HebcalService.nightfall()` opens every night window of a block's last day (maariv, the bedtime Shema, the Omer, the Chanukah candles, havdalah, a tevila) at the exit instead of tzeit, so none starts inside the quiet block. The Hebrew date still turns at tzeit, and a fast still ends at tzeit.
- Shabbat and Yom Tov are ordinary days for history and the streak (user decision 2026-10-06), marked after the fact. Everything whose window reaches into a block waits in that block's check-in until it is finished or until the alot that ends the first weekday after the block (`checkInDeadline(block, location)`); only then is a missing mark a miss. [checkIn.ts](src/utils/checkIn.ts) owns that, and [historyStats.ts](src/utils/historyStats.ts) judges every item done, missed or still open.
- A holy block is a maximal run of Shabbat / Yom Tov / Yom Kippur days at the location (second-day Yom Tov by `inIsrael`), from candle lighting on the erev to the exit of the last day, ten minutes after its tzeit: `HebcalService.holyBlockAt()` / `holyBlockOn()`. The app is never active inside one, and that is the only mode — the user ruled out any setting for it on 2026-10-06. No notification fires strictly inside a block (`isQuietAt()`), and the root layout covers every route with `ShabbatScreen`. The edges stay open, so candle lighting at the start and havdalah or maariv at the end still fire.
- `HebcalService` wraps `@hebcal/core` for Hebrew dates, parasha, holidays, yom tov, Daf Yomi, Omer, and Shabbat.
- Always pass `Location` to `HebcalService.isShabbat(date, location)` for halachic boundary behavior. Without a location it falls back to Gregorian Saturday only.
- Avoid UTC date shortcuts for mitzvah logic.
- The app's day turns at alot hashachar, not at midnight (the user's call, 2026-10-12: the night belongs to the evening before). `appDay(instant, location)` in [src/utils/locationDay.ts](src/utils/locationDay.ts) is "today" everywhere a day is shown or a mark is filed: home, history and the streak, the weekly report, the schedule, the day view, the reader's default date and the check-in deadline. Its boundary is `HebcalService.dawnAt()` (04:00 on the location's clock where the sun neither rises nor sets), and an item's day ends at `appDayEnd()`, the next alot. Between midnight and alot, maariv, the bedtime Shema, the Omer, the Chanukah candles, Chok LeYisrael and a custom mitzvah set across midnight stay on home until their window closes. Kiddush Levana stays on home every night and day of its period until marked. Every mark is filed under the day its window was computed for (`dateKey(window.date)`), the key its notifications carry. The Hebrew date in headers still turns at sunset.
- Two calendars meet here, and they disagree whenever the device's zone is not the location's. A day the app shows or keys (`dateKey()`, schedule cells, history rows, notification ids) is a location date, held as the device-local midnight of that date. Zmanim, Shabbat, Yom Tov and the Hebrew date belong to the location's. Never answer a location question through device-local getters:
  - `ZmanimService` and `HebcalService.isShabbat` / `isYomTov` / `getHebrewDateAt` resolve an instant's civil day in the location's zone.
  - Static `computeWindow`s take their weekday, next day and Omer count from the day `ctx.zmanim` belong to, at its midday — never from `ctx.date`, whose clock time depends on the caller. See [src/data/AGENTS.md](src/data/AGENTS.md).
  - Day-level surfaces turn a device calendar day into the same date at the location with `locationNoon()` from [src/utils/locationDay.ts](src/utils/locationDay.ts). Device-local midnight is the previous day at a location west of the device.
  - Custom mitzvah windows put the device's calendar date of `ctx.date` on the location's clock through Luxon, or the next date when the hours end at or before that date's alot (`HebcalService.dawnAt()`), so a custom window always overlaps the app day it is keyed under.

## Taharah Tracking

Taharat hamishpacha (the niddah cycle) is tracked on the device, behind an opt-in (`taharahEnabled`) that onboarding and Settings offer only to a married user who answered the gender question (`taharahOffered()` in [taharahOptIn.ts](src/stores/taharahOptIn.ts)). A single user never sees the topic. The app never rules: every safek stops the cycle until the user records the rav's instruction.

- Raw input only is stored: `TaharahEvent`s (onset with its onah, hefsek, bedika, tevila, pause, resume, ruling) in `useTaharahStore`, encrypted. Every state, task and perisha onah is replayed from them by the pure engine in [src/utils/taharah/](src/utils/taharah) (`deriveCycle()`, `taharahTasksFor()`, `perishaOnot()`, `kavuaHints()`, `stageHint()`), so a corrected rule is a replay, not a migration.
- The rules are individual parameters (`TaharahRules`) filled by a preset in [taharahPresets.ts](src/data/taharahPresets.ts): `ashkenaz`, `chassidic`, `chabad`, `sephardi_ovadia`, `sephardi_eliyahu`. [docs/taharah-review.html](docs/taharah-review.html) states every value with its source for a rav; a preset change raises `TAHARAH_RULES_VERSION` and edits that page in the same change.
- Days are hebcal absolute numbers and onot are counted night-first (`onahIndex`). An onset in bein hashmashot is doubtful: counted from the next day for the wait, and both onot are kept for the vestot.
- A tevila night that falls on Yom Kippur or Tisha B'Av is deferred to the next night. A woman records the hefsek and the bedikot before the tevila; the husband role records only onsets and the tevila night and sees only perisha onot, the tevila night and "did the period arrive".
- Nothing taharah-related is shown or fires inside a holy block; a reminder that would land there goes out before candle lighting, merged with the block's other taharah reminders.

## Notification Engine

[NotificationScheduler.ts](src/services/NotificationScheduler.ts) is the scheduling facade. Keep API parity with [NotificationScheduler.web.ts](src/services/NotificationScheduler.web.ts).

Module layout: the schedule is built by a one-way pipeline in [src/services/notifications/](src/services/notifications) — `readPlanInput()` reads the stores once into a `PlanInput`, `buildPlan()` runs pure planners (mitzvot, holy-block notice, hilulot, check-in, taharah) over it and returns channel-tagged `ScheduleCandidate`s sorted and capped, and `os.schedule()` is the only code that hands them to expo-notifications. The facade keeps the public exports, the lock, suppression and mark-done, the update notice, permissions, the handlers and both `defineTask` calls. [src/services/notifications/AGENTS.md](src/services/notifications/AGENTS.md) holds the contract.

Important constants and contracts:

- Categories: `mitzvah_reminder` (mark-done only) and `mitzvah_reminder_text` (open text + mark done), chosen per reminder by `hasSiddurText()`, except that a trigger on a block's opening edge (candle lighting) gets mark-done only: every screen it could open is behind the Shabbat screen
- Actions: `MARK_DONE` (background) and `OPEN_TEXT` (opens the app to `/siddur/[id]?date=`)
- Android channels (`ANDROID_CHANNELS`, planned per candidate): `default` for mitzvah reminders and the pre-block notice (the id is kept so installs keep the sound the user chose), `hilulot`, `rosh-chodesh`, `taharah` (private on the lock screen) and `system` for check-in reminders, the weekly report notice and the update notice. A reminder's `data.hasText` is the same decision as its category (`mitzvah_reminder_text` exactly when it is true) and sends the body tap to the reader. The channel table is in [src/services/AGENTS.md](src/services/AGENTS.md).
- Scheduled identifier format: `${mitzvahId}__${YYYY-MM-DD}__${reminderIndex}`, and `${reminderIndex}.${n}` for the n-th further trigger of a `blockExit` reminder; `parseId()` reads the index as an integer. A notification not tied to a mitzvah uses an id without `__` and carries `data.kind`: the pre-block notice is `blockNotice:<first holy day>`, with no category. The update notice is `update:<update id>`, `data.kind = 'update'` with `data.updateId`, presented at once, with no category. A hilula notice is `hilula:<hebrew abs day>:<before|evening>`, `data.kind = 'hilula'`, with no category. A Rosh Chodesh notice is `roshChodesh:<hebrew abs day>:<before|evening|day>`, `data.kind = 'roshChodesh'`, with no category. The weekly report notice is `report:<YYYY-MM-DD of the week's last day>`, `data.kind = 'report'` with `data.report = { week }`, with no category. The end-of-reminders notice is `horizonEnd:<YYYY-MM-DD>`, `data.kind = 'horizonEnd'`, with no category.
- Pending guard: `PENDING_LIMIT = 400` on Android and other platforms (under Android's 500 alarms per app), `IOS_MAX = 64` with `IOS_HEADROOM = 4`; `planCap(platform)` in [ids.ts](src/services/notifications/ids.ts) gives 400 or 60, the last slot belonging to the end-of-reminders notice.
- Horizon: `HORIZON_MAX_DAYS` (30) of the location's calendar days from today (the user's report of 2026-10-26: reminders stopped a day or two after the last open, because the OS may never run the background task); the first two days still stretch through any holy block that is reached or starts the next day, up to the first weekday after it, and that stretched prefix is never thinned. The plan is built in full and cut at the cap, furthest first. Each step is the device-local midnight of that location date with its zmanim read at the location's noon, so ids and completion keys name the window's own day and a DST change in either zone cannot skip or repeat one. Mitzvah reminders are planned for the two days before the horizon too, so a rebuild after midnight keeps the reminders still due in a window that opened yesterday (a custom mitzvah set across midnight) and a follow-up still due after a full-day window that opened the day before yesterday; a `multiDay` mitzvah is planned over its `maxDays` days before the horizon. Candidates are ordered by trigger time and cut at `planCap() - 1`, so an overflow drops the furthest-out reminders rather than all of tomorrow.
- Thinning: when the full plan holds more than the cap less one (iOS for a default set), `planMitzvot()` runs again from `horizon.thinFromIndex` (the day after the opening's holy-block stretch, the third day at least): from there each mitzvah window keeps its latest trigger at or before its end (a `followUp` and a `blockExit` trigger are dropped there; a window with only those keeps its earliest). Today, tomorrow and every other notice kind are never thinned.
- End-of-reminders notice (`planHorizonEnd()` in [planners/horizonEnd.ts](src/services/notifications/planners/horizonEnd.ts), `system` channel): at 20:00 on the location's clock (clamped into the open hours under quiet hours) on the last day the cut left whole (the horizon's last day when nothing was cut), or at the exit of the block that covers that hour; if that time has already passed when the cut lands that near, it goes out at the last kept trigger, at least five minutes from now and never inside a block. `notifications.horizonEnd.title` / `.body`; every rebuild moves it, so it fires only if the app stays closed; a tap opens home.
- Quiet hours (the owner's request, 2026-10-29): two independent bounds in Settings → Device and notifications, `quietBefore` ("no notifications before X", 07:00 when first switched on) and `quietAfter` ("no notifications after Y", 22:00), both off by default and held in `useUserStore` as `{ enabled, minutes }` on the location's clock. The pure clock rule is [src/utils/quietHours.ts](src/utils/quietHours.ts) and the block-aware `quietHoursTrigger()` sits beside `reminderFires()` in [src/utils/skipRules.ts](src/utils/skipRules.ts). A planned notification outside the open range moves to X, on the same location date when it falls before X and on the next date when it falls after Y. It is dropped instead when there is no X, when X is past the notification's own bound, or when X falls strictly inside a holy block (never deferred to the block's exit); a trigger already inside a block never moves. The bound of a mitzvah reminder is its window's end, or the end + 720 minutes for a follow-up, so `reminderFires()` judges the moved trigger; any other notice moves at most to the alot that ends its calendar date (`calendarDayEnd()` in [src/utils/locationDay.ts](src/utils/locationDay.ts)), so an after-Y notice is dropped unless X is before that alot. The open range is inclusive with seconds counted (22:00:00 fires, 22:00:30 moves) and valid only while at least 60 minutes stay open (a first hour alone up to 23:00, a last hour alone from 01:00, no range across midnight); the setters and the UI refuse a shorter one, and the planners treat an invalid pair as none. The rule runs inside each planner, before its past and block checks, so a rebuild at 06:00 keeps a 05:00 reminder moved to 07:00; ids, payloads, categories and `SCHEDULE_FORMAT` are unchanged, and only `contentHash` and the chosen body variant follow the moved time. Mitzvah reminders that land on one instant after a move are reduced to one (the later window day, then the lower reminder index; a coincidence with nothing moved stays), a moved hilula or Rosh Chodesh notice is worded from the moved phase, and the weekly report moves like a notice. Family purity follows `TAHARAH_QUIET_POLICY` in [src/services/notifications/planners/taharah.ts](src/services/notifications/planners/taharah.ts): the hefsek, the evening bedika, the onah bedika, the tevila and its preparation, perisha and the merged pre-block notification are exempt, the morning bedika moves only while the chosen time is before chatzot and otherwise fires on time, and the onset check and the post-block nudge move like any notice. The pre-block notice and the check-in reminders never move. The end-of-reminders notice clamps its 20:00 into the open hours and, when its exit or fallback time falls outside them, moves to X (or to the next date at the clamped hour) with no day bound, because it is the only warning that the reminders run out; the update notice presents nothing inside the quiet hours and the next hourly run outside them presents it, as for Shabbat. The mitzvah screen's next-reminder line and rows name the moved time, each row its own even when the move leaves one notification at that instant; the reminder editor passes no quiet hours and describes the reminder's own time. A change of `quietBefore` or `quietAfter` rebuilds the schedule.
- Check-in reminders (`checkin:<firstHolyDay>:<0|1|2>`, `data.kind = 'checkin'`, no category) fire at a block's exit, two hours later, and at 20:00 on the location's clock the next day — or half an hour before the next block's candle lighting when that evening is already holy — until the check-in is finished or everything in it is marked or skipped, and never at or after its deadline, the alot that ends the first weekday after the block (`checkInDeadline()`). A mark that settles the check-in withdraws them at once (`settleCheckIn()`). `cancelCheckIn()` withdraws them and clears the tray; the foreground handler suppresses one for a finished check-in.
- The pre-block notice fires an hour before candle lighting for every user with notifications on: title by block kind, lighting and exit times, the Omer counts of the block's nights when `sefirat_haomer` is enabled, a line for each hilula whose notice the block swallows when `hilulotEnabled` is on, a line for each Rosh Chodesh notice it swallows when `roshChodeshEnabled` is on, and a line naming the Ushpizin guest of each night inside the block when `ushpizin` is enabled (`holyBlock.notice.ushpizinTonight` for the erev's night, else `ushpizinOn` with the weekday); only the notice kinds switched on count, at the times they are set to.
- Hilula notices (`hilula:<abs>:<before|evening>`) exist only while `useUserStore.hilulotEnabled`: one for each kind switched on in `useUserStore.hilulaNotices`: `evening` on the day whose shkia opens a tzaddik's date, `before` on the day `daysBefore` days before the evening that opens that date (1–7, one by default, so the day before the evening notice), each at its `timing`, the shkia or up to 180 minutes before it, or a clock time on the location's clock (both at the shkia by default, the schedule of 2026-10-08), for the core list in [src/data/hilulot.ts](src/data/hilulot.ts). The `evening` text follows where the notice fires against the shkia that opens the date: entering tonight before it, entering now at it, and begun after it (`hilulot.notice.evening.titleBegun` / `bodyBegun`). They are a setting, not a mitzvah: the library lists them as a row (the user's call, 2026-10-08), but they stay out of `MITZVOT`, so they never reach history, the streak, home's mitzvah lists, the check-in or `MARK_DONE` (a hilula of today or tonight shows on home only as a Messages row).
- Rosh Chodesh notices (`roshChodesh:<abs>:<before|evening|day>`) exist only while `useUserStore.roshChodeshEnabled`, one for each kind switched on in `useUserStore.roshChodeshNotices` (three kinds, the user's call, 2026-10-11; configurable since 2026-10-24): `before` on the day `daysBefore` Hebrew days ahead of its first day (1–7, three by default), `evening` on the day whose shkia opens it, and `day` on each of its days, so a two-day Rosh Chodesh gets two; each fires at its `timing`, the shkia (or up to 180 minutes before it) or a clock time on the location's clock, by default 20:00, the shkia and 07:00. The id's `abs` is the new month's first day for `before` and `evening` and the notice's own Hebrew day for `day`; the title names the new month in the UI language (`roshChodeshLabel()`: plain Adar, Adar I and Adar II in Hebrew and English), the `before` title the days left (`roshChodesh.notice.inDays.<n>`), the `before` body names the weekday of the evening the month enters, or says it enters tonight when the notice is one day ahead; a `before` or `evening` notice that fires after the shkia that opens the month says it has begun (`roshChodesh.notice.begun.*`). The day arithmetic is [src/data/roshChodesh.ts](src/data/roshChodesh.ts), the planning [planners/roshChodesh.ts](src/services/notifications/planners/roshChodesh.ts). It is a setting like the hilulot, not a mitzvah: a library row beside the hilulot row, no switch in Settings, and out of `MITZVOT`, history, the streak, home's mitzvah lists, the check-in and `MARK_DONE` (a Rosh Chodesh within seven days shows on home only as a Messages row). A notice strictly inside a holy block is not scheduled; `roshChodeshLines()` names it in that block's pre-block notice instead (`roshChodeshTonight` when the month enters at the erev's shkia, else `roshChodeshOn` with the weekday, and with its date as well when the month enters seven or more days after the erev (`noticeDayLabel()`); `roshChodeshDay` for a notice of the day, once per day).
- The weekly report notice (`report:<week end>`, `system` channel, no category) exists while `useUserStore.weeklyReportEnabled`, on by default (the user's call, 2026-10-11). It is planned for the block that closes the week, the one that holds a Saturday: motzaei Shabbat, or the exit of a Yom Tov that follows it, where the week end is the block's last day; a Yom Tov in mid-week has none (`weekEndFor()` in [src/utils/weeklyReport.ts](src/utils/weeklyReport.ts), planned by [planners/report.ts](src/services/notifications/planners/report.ts)). It fires `REPORT_DELAY_MIN` (45) minutes after the block's exit, after the check-in's first nudge (at the exit) and before its second (two hours on), and a tap opens `/report` on that week. The report is computed from the stores when the screen opens, not frozen at notification time, so its numbers settle as the check-in is finished; the text is local templates. Settings keeps its switch (`settings.weeklyReport`) in the notifications block of the device section; past reports come from the reports list in the history tab's מגמות. It is a setting, not a mitzvah: it never reaches history, the streak, home or the check-in.
- Taharah reminders (`taharah:<task>:<hebrew abs day>[:<onah>]`, `data.kind = 'taharah'`) are built from `taharahTasksFor()` for every horizon day when the feature is on: hefsek before shkia, the two daily bedikot (category `taharah_bedika`, whose `MARK_DONE` records a clean bedika), tevila prep and tevila at nightfall (tzeit, or a block's exit on motzaei Shabbat), perisha onot, the onah-beinonit bedika, "did the period arrive", a `postBlock` nudge after a block with unrecorded bedikot, and one merged `preBlock` notification for everything a block would have swallowed. Discreet wording is the default. [src/services/AGENTS.md](src/services/AGENTS.md) holds the details.
- Daily rebuild task: `jew-365-daily-rebuild`, an `expo-background-task` task registered with `minimumInterval: 60` (minutes; the OS decides the real cadence). Its rebuild is gated by `notifications:last-rebuild-date` and intended to run once per local day at/after 00:15; every run also calls `notifyIfUpdateReady()`.
- Background notification action task: `jew-365-notification-actions`.
- Delivery must stay EXACT. expo-notifications only calls `setExactAndAllowWhileIdle` when `AlarmManager.canScheduleExactAlarms()` is true, and there is no JS API to detect the fallback — so the manifest is the only guarantee. `USE_EXACT_ALARM` covers API 33+, `SCHEDULE_EXACT_ALARM` (capped at `maxSdkVersion=32` by [scripts/withExactAlarmPermissions.js](scripts/withExactAlarmPermissions.js)) covers Android 12. Pinned by [exactAlarmConfig.test.ts](src/services/__tests__/exactAlarmConfig.test.ts).
- The battery exemption is requested through the system dialog (`requestIgnoreBatteryOptimizations()` in [src/services/deviceSettings.ts](src/services/deviceSettings.ts), the owner's call, 2026-10-28), falling back to the battery list and then the app's settings page.

Behavior to preserve:

- `scheduleAll()` and `rebuild()` go through `withLock()`, which coalesces on the trailing edge: a request arriving mid-run queues exactly one re-run so the newest state is always applied.
- `rebuild()` cancels everything and schedules the plan when the stored `SCHEDULE_FORMAT` stamp is stale, when `rebuildForNewDay()` runs (once a day), and, on Android, on the first rebuild of each JS process: a force-stop removes every alarm but keeps expo's stored requests, so a diff against `getAllScheduledNotificationsAsync()` would never re-arm them. With notification permission gone it only cancels. Otherwise `os.sync()` cancels the pending ids the plan lacks or whose `data.contentHash` changed and schedules only the new and the changed. Only `rebuildForNewDay()` records the last rebuild date, so a settings-driven rebuild cannot suppress the nightly recovery run.
- A plan holds nothing for disabled or no-permission cases, Shabbat/Yom Tov skips, `null` windows, skipped or completed mitzvot for that date, past triggers, and any trigger strictly inside a holy block.
- `cancelForMitzvah(id, date)` cancels all pending reminders for that mitzvah/date and dismisses the presented ones, so marking a mitzvah done anywhere clears it from the tray and prevents later same-day notifications. Every mark carries the day its window was computed for: screens pass `window.date` (or the reader's `date`), and `MARK_DONE` the notification's `data.dateKey`, so the cancel reaches that window's ids even when the mark comes after midnight.
- A presented mitzvah reminder leaves the tray once its app day has ended (`appDayEnd()` of its `dateKey` day, never before the end of the app day it was shown on), at launch, on every return to the foreground and on every run of the hourly task, because Android drops new notifications once an app holds about 50 in the tray; a mark-done from the tray before then works as always, and every other kind keeps its own rule ([src/services/notifications/AGENTS.md](src/services/notifications/AGENTS.md)).
- The mitzvah screen's "next reminder" line is `nextReminderAt()`, exported by both scheduler files: the first trigger after now that the plan's per-window rule (`windowTriggers()`, which `planMitzvot()` uses too) lets through, over the next ten days, so after a window's last reminder it names the next window's first one, past any holy block. It is the earliest trigger over the whole range, so a later window's heads-up that comes before an earlier window's last reminder is named first. It names the configured reminder: on iOS, when the full plan does not fit, the scheduler keeps one reminder per window from the third day, so a reminder named for a day beyond tomorrow may not be among those scheduled.
- A language change rebuilds the schedule, because notification text and button titles are translated at scheduling time.
- `SCHEDULE_FORMAT` (10 since the payload gained `contentHash`) is raised whenever a scheduled notification changes shape, so the first foreground after an update rebuilds once. A newly default-on mitzvah needs no raise: when the module-scope `applyGenderDefaultsToNew()` in [NotificationScheduler.ts](src/services/NotificationScheduler.ts) returns any id the mitzvot hydrate added, that module drops the stored stamp (`SCHEDULE_FORMAT_KEY`), so the next foreground, in that process or a later one (a headless launch or an RTL reload took the ids first), rebuilds once and schedules it.
- `useCompletionsStore.markDone`, `markSkipped`, and `unmark` also trigger notification cancellation/rebuild through a queued `require()` to avoid import cycles.
- `initNotificationHandlers()` is called from [_layout.tsx](src/app/_layout.tsx) after fonts load and returns a teardown the layout runs on unmount. It also calls `refreshSchedulingOnForeground()`, which home repeats on `AppState 'active'` so the horizon cannot silently expire. It sets the foreground handler, registers category/action tasks, syncs permission, dismisses presented notifications that are already completed or whose day has ended, subscribes to store changes, and registers the daily rebuild task.
- Tapping the notification body routes to `/mitzvah/[id]`; tapping `OPEN_TEXT` routes to `/siddur/[id]` with the notification's `dateKey`, buffered like the body tap on a cold start; tapping `MARK_DONE` marks completion without foregrounding the app. The pre-block notice opens home, a check-in reminder opens `/checkin`, a hilula notice opens `/hilula/[id]` on the first tzaddik it names (`data.hilula.ids`, with all of them as `ids` when there are two or more), or `/hilulot` for one scheduled with no ids, a Rosh Chodesh notice opens `/rosh-chodesh`, a weekly report notice opens `/report` on its week, and an update notice reloads into its update, or opens home when that update, or a newer one, is already running (`isUpdateApplied()`). Inside a holy block a tap opens nothing (only `MARK_DONE` still runs), and a tap buffered on a cold start before the block is dropped rather than replayed into it.
- [withMitzvahNotificationAction.js](scripts/withMitzvahNotificationAction.js) is an Expo config plugin that writes an Android Kotlin service to dismiss a notification after the mark-done action. Keep this in mind when changing notification action IDs.
- Both `TaskManager.defineTask` calls live at [NotificationScheduler.ts](src/services/NotificationScheduler.ts) module scope, and the bundle entry is the root [index.js](index.js) (the `main` field in [package.json](package.json)), which imports [src/services/crashReporting.ts](src/services/crashReporting.ts) first, so Sentry is up in a headless launch too, then the router entry and that module. A killed-state `MARK_DONE` tap and a background task arrive as headless launches that never load route modules — a `defineTask` reachable only through the router tree never runs and the OS-invoked event is silently dropped. Pinned by [backgroundTaskEntry.test.ts](src/services/__tests__/backgroundTaskEntry.test.ts). The same module scope calls `applyGenderDefaultsToNew()` ([taharahOptIn.ts](src/stores/taharahOptIn.ts)) once, after the user and mitzvot stores it imports have hydrated (MMKV hydrates synchronously), so a launch that never loads the layout (the hourly task, a `MARK_DONE` tap) still switches a men's mitzvah the hydrate just added off for a woman, and saves it off, before any plan reads the store; the root layout's later call finds nothing left and covers web, whose scheduler is the shim. Pinned by [NotificationScheduler.headless.test.ts](src/services/__tests__/NotificationScheduler.headless.test.ts).

The web scheduler file is intentionally a no-op shim. If adding exported scheduler helpers, add matching exports to both native and web files.

## State and Persistence

All primary stores use Zustand with MMKV persistence through `StorageService.createZustandStorage()`, except `useTaharahStore`, which persists to its own encrypted instance. Every store passes `version` and the identity `migrate` from [persistOptions.ts](src/stores/persistOptions.ts): without a `migrate`, zustand discards the persisted state on a version mismatch.

- `useUserStore` (`user-store`): nusach, location (re-resolved from [src/data/cities.ts](src/data/cities.ts) on every hydrate by its `cityId`, so a corrected city reaches installs that already picked it; a GPS location follows the phone on every launch and return to the app through `followDeviceLocation()` in [src/services/locationFollow.ts](src/services/locationFollow.ts), while a city picked by hand stays fixed), theme (one of the six palette names), the display size (`uiScale`, one of the seven `UI_SCALES` steps of [src/theme/scale.ts](src/theme/scale.ts), `1` by default), language, notification permission/toggle, profile fields, halachic opinions, in-Israel flag, onboarding flag, the reader's text size and auto-scroll (`siddurAutoScroll`, off by default, and `siddurScrollSpeed`, a level into the 15 `SIDDUR_SCROLL_SPEEDS`), `siddurCompassPrompt` (on by default and for an older payload; the Settings switch writes it; whether the reader offers the compass on opening Shacharit, Mincha and Maariv), `prayerMode` (`minyan` or `alone`, `minyan` by default; `alone` folds the minyan-only passages in the siddur reader), the siddur voice (`siddurVoice`: `male`, `female` or `null`, `null` by default; `chooseGender()` sets it on every change of gender, and the reader shows a wording or a passage marked for one voice only to that voice, while with `null` it reads the text as printed and keeps such a passage folded; a passage folded for one voice only (`foldsFor`) reads open for the other voice and for `null`, and the siddur tab lists no `tefillin` text for the `female` voice), the home screen's look (`homeLook`: `rings`, `cards` or `rail`, `rail` by default), the hilula notices switch (`hilulotEnabled`, off by default), the Rosh Chodesh notices switch (`roshChodeshEnabled`, off by default), the notice kinds of each (`hilulaNotices`, `roshChodeshNotices`: `{ enabled, daysBefore?, timing }` per kind, all on at the 2026-10-08 times by default; a switch with every kind off cannot be switched on, and the last kind cannot be switched off while it is on), the weekly report switch (`weeklyReportEnabled`, on by default), the quiet hours (`quietBefore` and `quietAfter`, each `{ enabled, minutes }` with the minutes after midnight on the location's clock, both off by default at 420 and 1320, the minutes kept while a bound is off; a setter refuses a pair that leaves less than 60 minutes open, the merge turns both bounds off for a stored pair that does, and `STORE_VERSION` stays), the Chok LeYisrael double-week choice (`chokDoubleChoice`: `first`, `second` or `both`, `null` until a double week first asks), the Chok LeYisrael commentary choice (`chokCommentaryOpen`, off by default: whether Rashi and Bartenura start open in the reader), the Chok LeYisrael ליל שישי day (`chokThuNightDay`: `thu` or `fri`, `null` until the reader's first "סיימתי" on ליל שישי asks), `gender` and `maritalStatus` (`married` or `single`), each `null` until answered, taharah opt-in.
- `useMitzvotStore` (`mitzvot-store`): enabled state and custom reminders per mitzvah. A mitzvah is switched on only while it has at least one effective reminder (`canEnable()`; the user's rule, 2026-10-24), the last reminder of an enabled mitzvah cannot be deleted, and a persisted empty `customReminders` hydrates as the defaults; a default-on mitzvah an existing install's map lacks (or an onboarded install with no map at all, which starts from the five original defaults; a fresh install, not yet onboarded, has every default-on id stamped with its first launch) is added on, stamped at that hydrate, and written once `applyGenderDefaultsToNew()` runs ([NotificationScheduler.ts](src/services/NotificationScheduler.ts) at module scope on every native launch, headless included; the root layout at load, for web; `restoreBackup()`); [src/stores/AGENTS.md](src/stores/AGENTS.md) holds the contract.
- `useCompletionsStore` (`completions-store`): `completions[YYYY-MM-DD][mitzvahId] = timestamp` and a parallel `skipped` map, both keyed by the day the window was computed for (`dateKey(window.date)`, so a night window marked after midnight files under the previous date), `checkIns[firstHolyDay] = finishedAt`, and `archivedDays` — runs of kept days that retention pruned, so the streak reaches past 400 days. It also holds `achievements` (badges by the day reached, longest streak, best week, each mitzvah's longest streak and the fold checkpoint; only ever raised, through `mergeAchievements()` / `saveAchievements()`) and `archivedMarks` (`archiveMarkCounts()`: the marks retention prunes, each day once by `lastKey`); `reset()` clears both. A screen always passes the window's day to `markDone`, `markSkipped` and `unmark`; their `date = new Date()` defaults serve tests only. A mark whose window has already closed asks when it was done (the owner's call, 2026-10-29; [useLateMarkDialog()](src/hooks/useLateMarkDialog.tsx) on home's My day, the mitzvah screen, the day view and the reader; the check-in never asks and files a closed window as a mark in time): in time but not marked is filed one minute before the window closed and counts as a mark in time everywhere; after the time passed is a late mark, in `completions` and in the parallel `late` map, and counts as done everywhere (the owner's call, 2026-10-30): home's day, the streak, the notifications, every percentage, the calendar, trends, the weekly report, each mitzvah's run and every badge; the `late` map only tags it, for the in-time shares, the per-mitzvah late counts, the 12-week late chart, the To improve card, the weekly report's late lines and the in-time badges (`punctualWeek`, `punctualMonth`, `fewerLate`), and [late-marks.tsx](src/app/late-marks.tsx) lists them. A notification's mark-done cannot ask and stays a plain mark.
- `useCustomMitzvotStore` (`custom-mitzvot-store`): user-created mitzvah definitions, each with its `schedules` (an optional field: no `STORE_VERSION` bump).
- `useTaharahStore` (`taharah-store`): the taharah event log, minhag settings and reminder leads, in an MMKV instance encrypted with a key held in `expo-secure-store` ([TaharahStorage.ts](src/services/TaharahStorage.ts)).
- `useChokStore` (`chok-store`): the installed add-on (version, bytes, each parasha's file), the latest version seen online and when it was checked; the download progress and the post-download enable prompt (`enablePrompt`, asked by [ChokEnablePrompt](src/components/ChokEnablePrompt.tsx), which the root layout mounts once) live in memory only. Device-only, so it stays out of the backup file; its `merge` drops an install whose files are gone (an Android restore carries the store but not the files), and a failed read does the same.
- `useSelichotStore` (`selichot-store`): the installed Selichot file (one nusach: version, bytes, file name), the latest version seen online, when it was checked and `dismissedSeason` (the Hebrew year of the season whose home offer was dismissed); the download progress lives in memory only. Device-only like `chok-store`; its `merge` drops an install whose file is gone.
- `useSiddurBookmarksStore` (`siddur-bookmarks-store`): the siddur reader's bookmarks and each text's last reading position, keyed by the reader's text id and the text's nusach (`null` for Chok LeYisrael and the texts every nusach shares); in the backup file and the main MMKV file.

[zustandMiddleware.ts](src/stores/zustandMiddleware.ts) deliberately requires `../../node_modules/zustand/middleware.js`. Do not replace it with a direct ESM import unless Metro and Jest are both verified.

`AppResetService.reset()` cancels notifications, resets all stores, and clears MMKV on native, including the taharah data and its key.

Backup and restore (the user's call, 2026-10-14) keeps the five plain stores across a reinstall or a new phone, never the taharah store:

- Android Auto Backup and device-to-device transfer carry only the main MMKV file (`files/mmkv/jew-365` and its `.crc`) and React Native's RTL preference, the whitelist in [scripts/withAndroidBackupRules.js](scripts/withAndroidBackupRules.js). Everything else stays out: the taharah files, expo-notifications' saved reminders, expo-updates' bundles, the secure store. A restored install has no scheduled reminders, so the first foreground finds none pending and rebuilds. On iOS the app's Documents folder, MMKV included, rides the device's iCloud backup; a delete and reinstall loses it, which the backup file covers.
- The backup file is [BackupService.ts](src/services/BackupService.ts): `{ app: 'jew-365', format, createdAt, stores }` with each store's persisted string as is; a file whose `app` is any tag in `RESTORABLE_APPS` restores, the previous app's included. Settings exports it through the share sheet (`expo-sharing`) and restores it through `File.pickFileAsync()`; onboarding's welcome step offers the restore too. A restore replaces, never merges: each store in the file is written and rehydrated through its own `migrate` and `merge`, a store the file lacks is reset, scheduling is suspended for the swap, the schedule stamp is dropped first so a reload part-way still rebuilds, and the schedule is rebuilt once. `chok-store` and `selichot-store` stay out of the file; a restored install downloads the add-ons again.

## UI, Theme, RTL, and i18n

- The app loads Heebo font weights in [_layout.tsx](src/app/_layout.tsx).
- Use `useTheme()` and `src/theme/*` tokens. Avoid hard-coded colors in new UI unless there is a narrow reason.
- Six palettes live in [src/theme/colors.ts](src/theme/colors.ts): gold (the default, a warm cream page with warm-white cards and an orange accent, the owner's 2026-10-21 redesign), pink, purple and blue (gold's style in a rose, violet and blue hue: a tinted page, a card of white warmed toward that hue at gold's card-to-page step, a separate `goldText` and soft shadows tinted to the hue; the 2026-10-25 rework), dark (night navy with the orange accent) and plum (dark plum with a rose accent); every palette's header is the page itself, drawn on `bg`, `text`, `textSub` and `goldText` (the tab bar on `tabBg`), so no screen draws a coloured header band, except home's hero, whose sky is the fixed scene palette of [src/theme/sky.ts](src/theme/sky.ts). They are chosen in Settings as colour circles with no visible labels, each the palette's page around a ring of its card and a dot of its accent (a change of gender switches to that gender's palette first, `paletteForGender()`). `gold` / `onGold` / `goldLight` are each palette's accent tokens, `goldWash` / `goldWashStrong` the accent as a faint tint (`goldWash` the schedule's current row, `goldWashStrong` the settings focus highlight and a calendar range's days), `goldText` is the accent's text tone, a colour of its own at 4.5:1 or more on the card (the gold palette's orange reads 2.5:1 there), `onUrgent` is the label colour on an `urgent` fill, `overlay` is the scrim behind sheets and dialogs, and `isDark` is true for the two dark palettes (`DARK_THEMES`). `BRAND` (`navy`, `gold`, `onGold`, `parchment`, `white`) holds the palette-independent brand colours, the default palette's identity, that the provider-free error boundary and a Switch thumb use; the logo has its own generated colours.
- The type scale in [src/theme/typography.ts](src/theme/typography.ts) is display 28, title 22, heading 17, subheading / body / bodyBold 15, caption / captionBold 13, small 12 and micro 11. Spacing and radius come from [src/theme/tokens.ts](src/theme/tokens.ts) (`spacing` xs 4 to xxxl 40, `radius` xs 4 to xxl 24 and full). These are the sizes at the default display size: Settings → Device → Display offers seven steps (80% to 120%, `UI_SCALES` in [src/theme/scale.ts](src/theme/scale.ts), 100% by default), the owner's request of 2026-10-26, and `scaled()` of that file multiplies every font size, line height, spacing and radius by the step saved in `useUserStore.uiScale`, read once at launch, so a change reloads the app; any new literal size in a component goes through `scaled()` ([src/theme/AGENTS.md](src/theme/AGENTS.md)).
- Translation tables are flat JSON dictionaries in [he.json](src/i18n/he.json) and [en.json](src/i18n/en.json); tests enforce key parity and non-empty values.
- `setLocale()` and `useI18n()` are lightweight wrappers. The `i18n-js` package is installed but the current app does not rely on the normal `i18n-js` runtime API.
- Weekday and month names come only from `formatDate(date, pattern, language)` in [src/i18n/index.ts](src/i18n/index.ts). It reads the names from the dictionaries (`weekday.long.0`–`6` and `weekday.short.0`–`6`, Sunday first; `month.long.1`–`12` and `month.short.1`–`12`) and the numbers from Luxon's getters, never from `Intl`. It takes `cccc`, `ccc`, `LLLL`, `LLL`, `d`, `M` and `yyyy`; any other letter run throws. A `DateTime` is read in its own zone and a `Date` on the device clock. Luxon builds names from `Intl.DateTimeFormat().formatToParts()`, which Hermes on iOS does not fill, so a `toFormat` with `ccc`, `LLL`, `EEE` or `MMM`, or a `weekdayLong`-style getter, reads "null" on an iPhone in Hebrew (any locale but English; Luxon's own English tables never touch `Intl`). [designSystem.test.ts](src/app/__tests__/designSystem.test.ts) fails on one anywhere under [src/](src) outside tests.
- RTL is dynamic based on `useUserStore.language`. `_layout.tsx` calls `I18nManager.allowRTL/forceRTL`; native language direction changes can require a reload.
- Web also sets `document.documentElement.dir/lang` and `body.dir`.
- The tab navigator in [src/app/(tabs)/_layout.tsx](<src/app/(tabs)/_layout.tsx>) passes `detachInactiveScreens={false}` on every platform, so `react-native-screens` never detaches a tab natively, and sets no `freezeOnBlur`: `@react-navigation/bottom-tabs` before 7.18.8 derived a tab's detached state from its `fade` animation value, which under Fabric on iOS sometimes left the focused tab detached, a blank page under a visible tab bar. The app carries 7.18.8, which fixes that upstream, and keeps the option as a second guard. Under 7.18.8 the focused tab is always `display: 'flex'` and an inactive tab is `display: 'none'` once the fade ends (before, it stayed `flex`), which on iOS under Fabric drops its native views until it is focused again. The contract and its suite are in [src/app/AGENTS.md](src/app/AGENTS.md).
- Main reusable UI components: `MitzvahCard`, `CompletedRow`, `Reveal`, `ReminderEditor`, `TimeRibbon`, `BottomTabs`, `NavBar`, `AppLogo`, `ShabbatScreen`, `ChipRow`, `SettingsSection`, `DayStepper`, `OnboardingDots`, `ChoiceRow`, `ThemeSwatchRow`, `ScrollSpeedStepper`, `TaharahLock`, `ScreenHeader` / `HeaderPill` / `CounterPill`, `SegmentedControl`, `ProgressBar`, `ConfirmDialog`, `BottomSheet` / `SheetAction`, `Banner`, `SectionLabel`, `ListRow`, `Card`, `IconTile`, `MitzvahIcon`, `DayArcHero`, `DaySkyScene`, `NowCard`, `DayLooks`, `MarkStamp`, `ChokWeekControls`, `ChokAddonCard`, `AddonCard`, `SelichotAddonCard`, `ChokLicenseNotice`, `NoticeSettingsCard`, `MitzvahLibraryList`, `Button`, `StreakRing`, `Landscape`, `OptionSelect` (a select field, or with `inline` a radio list inside a sheet), `ReminderTimingFields` (the shared reminder timing editor) and `PickerCard`.
- Design-system rules, each guarded by [designSystem.test.ts](src/app/__tests__/designSystem.test.ts) where a source scan can check it:
  - A stack screen renders `ScreenHeader` (back pill, title, `actions`); a tab renders `NavBar`. Neither keeps a local back button or header style.
  - Icons come from `MitzvahIcon` / `IconTile`, a mitzvah's through `iconFor(mitzvah.icon)`; no text glyph stands in for one.
  - A segmented choice is `SegmentedControl`, a confirmation `ConfirmDialog`, an action sheet or picker `BottomSheet` with `SheetAction`, a select field `OptionSelect`, a status strip `Banner`, a list heading or field label `SectionLabel`, an icon-title-caption row `ListRow`, a card or grouped list `Card`, a header counter `CounterPill`, a full-width action `Button`, the mitzvot list with its switches `MitzvahLibraryList`, and a pill row `ChipRow`; a screen never keeps a local copy and renders no `Modal` of its own.
  - No spacing or radius literal where a token matches, no white literal (`onGold`, `onUrgent` or `BRAND.white`), and no `fontWeight` on Heebo text (a `typography` variant or `fontFamilies.heebo`). No translucent white (`rgba(255,255,255,…)`), no file reading a `colors.header*` token (they no longer exist), and no screen-local `card`, `primaryBtn`, `dangerBtn`, `secondaryBtn` or `cta` style.

Test rules that exist because the suite once passed while the app was broken:

- A test must import the shipped implementation. Re-declaring the logic under test asserts only that the test agrees with itself.
- Assert values, not types. `expect(typeof x).toBe('boolean')` passes for both answers.
- A test must be able to fail for the reason it claims. `planMitzvot` (run through `buildPlan`) drops every trigger before `input.now`, which is the real clock unless a test passes one, so fixtures in the past pass vacuously; derive dates from `Date.now()` instead.
- A fixture must mean the same moment in every zone. `new Date(2026, 3, 24, 20)` is 20:00 on the device's clock, so build an instant for an instant API with `at(location, '2026-04-24T20:00')` from [src/testing/zmanim.ts](src/testing/zmanim.ts). Calendar-day APIs (`dateKey`, `getHebrewDate`, `getHolidays`, and `isShabbat` / `omerDayFor` without a location) read device-local dates, so they take local-component dates. The app's day (`appDay()`, `appDayEnd()`), `appDayWindow()`, `currentOrNextWindow()`, `computeStats()`, `judgeDay()` and the check-in deadlines read an instant against the location's alot, so they take `at(location, …)` instants, never a device-local `new Date(y, m, d, h)`, which lands on a different date at the location in other zones.
- Run [pnpm test:tz](scripts/test-timezones.js) after touching date or timezone logic. It runs every suite in four real zones, and a setup guard fails any run whose zone did not take effect.
- A suite that schedules notifications pins `Date` (and only `Date`) to a fixed weekday. Nothing fires inside a holy block, so on the real clock the suite would fail every Shabbat. Faking timers or `queueMicrotask` too would stall the completion store's queued side effects.

## Search Finds Everything

A binding rule, the owner's of 2026-10-27, that no change may skip: the search at the top of Settings and of the More tab finds everything in the app, from the largest item to the smallest, by its name, a near name or a misspelling.

- In scope: every screen and tab, every setting, every mitzvah (custom ones included), every library and siddur category, every siddur text, chapter, section and passage, every tzaddik with his aliases, works and grave, every halacha line and its rav, every guide topic, every tracking card, figure and badge with the user's own value, and every city.
- A change that adds, renames or removes any of these updates the search in the same change, never later. A setting goes into `SETTINGS_SEARCH_ITEMS`. A screen goes into `SEARCH_SCREENS`. Content goes into `settingsContentItems()` or `appContentItems()`. Siddur text is read by the deep pass. All of these live in [src/utils/settingsSearch.ts](src/utils/settingsSearch.ts). The change also adds the words people would type for it, in Hebrew and English. A result must open exactly where the item is, through a route param when the screen needs one (`focus`, `tab`, `topic`, `group`, `open`, `section`, `segment`).
- Results come in two tiers. Close matches (exact, prefix, substring) show at once. Near misses (typo tolerance) show after them under "אולי התכוונת", never among the close ones. A deep pass over the siddur texts and the current streak runs in the background after typing pauses. It never blocks a keystroke, and its results join each tier when it ends ([src/components/SettingsSearch.tsx](src/components/SettingsSearch.tsx)).

## Animations Start When Seen

A binding rule, the owner's of 2026-10-28: an entrance animation (one that plays because an element appeared) starts only when its element is on screen, never at mount below the fold.

- It plays every time its element comes on screen (the owner's call of 2026-10-29, replacing once per visit): it counts as gone once wholly off screen and as back once `motion.visibleShare` of it is on screen again, so scrolling away and back replays it and an edge sliver never flickers it; coming back from another tab replays it (`useReplayKey()` in [src/hooks/useIsFocused.ts](src/hooks/useIsFocused.ts)); popping a pushed stack screen back over the tab does not, and a stack screen replays on its next mount.
- The gate is `useInView()` in [src/hooks/useInView.ts](src/hooks/useInView.ts): at least `motion.visibleShare` of the element inside the window, measured on mount, on layout and on every throttled notice of the scroll container for as long as it is mounted (`isOutOfViewport()` marks it gone). A screen whose scroll container holds a gated element wraps it in `ViewportContext.Provider` from `useViewport()` and wires `notify` to `onScroll` and `onContentSizeChange`. Outside a provider, and under reduced motion, an element counts as seen at once.
- Build an entrance from [Reveal](src/components/Reveal.tsx), `useEntrance()` or `usePop()` with a gate from `useInView()`; never a reanimated `entering=` prop, which fires on mount. Interactions (a press, a mark, a choice, live data) stay ungated and are listed by name in the tripwire.
- [src/app/__tests__/designSystem.test.ts](src/app/__tests__/designSystem.test.ts) fails on an `entering=` prop, a reanimated animation builder outside its interaction allowlist, a React Native `Animated` timing, an ungated `useEntrance()` / `usePop()` call, a `layout=` prop, a reanimated namespace import and a builder anywhere under [src/](src) outside the allowlist (`hooks/useMotion.ts`, which defines them, included), and a screen with a gated animation but no viewport provider.

## DOX Framework

- DOX is highly performant AGENTS.md hierarchy installed here
- Agent must follow DOX instructions across any edits

## Core Contract

- AGENTS.md files are binding work contracts for their subtrees
- Work products, source materials, instructions, records, assets, and durable docs must stay understandable from the nearest applicable AGENTS.md plus every parent AGENTS.md above it

## Read Before Editing

1. Read the root AGENTS.md
2. Identify every file or folder you expect to touch
3. Walk from the repository root to each target path
4. Read every AGENTS.md found along each route
5. If a parent AGENTS.md lists a child AGENTS.md whose scope contains the path, read that child and continue from there
6. Use the nearest AGENTS.md as the local contract and parent docs for repo-wide rules
7. If docs conflict, the closer doc controls local work details, but no child doc may weaken DOX

Do not rely on memory. Re-read the applicable DOX chain in the current session before editing.

## Update After Editing

Every meaningful change requires a DOX pass before the task is done.

Update the closest owning AGENTS.md when a change affects:

- purpose, scope, ownership, or responsibilities
- durable structure, contracts, workflows, or operating rules
- required inputs, outputs, permissions, constraints, side effects, or artifacts
- user preferences about behavior, communication, process, organization, or quality
- AGENTS.md creation, deletion, move, rename, or index contents

Update parent docs when parent-level structure, ownership, workflow, or child index changes. Update child docs when parent changes alter local rules. Remove stale or contradictory text immediately. Small edits that do not change behavior or contracts may leave docs unchanged, but the DOX pass still must happen.

## Hierarchy

- Root AGENTS.md is the DOX rail: project-wide instructions, global preferences, durable workflow rules, and the top-level Child DOX Index
- Child AGENTS.md files own domain-specific instructions and their own Child DOX Index
- Each parent explains what its direct children cover and what stays owned by the parent
- The closer a doc is to the work, the more specific and practical it must be

- Create a child AGENTS.md when a folder becomes a durable boundary with its own purpose, rules, responsibilities, workflow, materials, or quality standards
- Work Guidance must reflect the current standards of the project or user instructions; if there are no specific standards or instructions yet, leave it empty

## Links

- Every reference to a project file or folder must be a relative Markdown link to that path, not plain text, so any reader can open it directly
- This applies to every Child DOX Index entry and to any inline mention of a concrete file or folder in a DOX doc
- Link targets are relative to the directory of the AGENTS.md that contains them, so they resolve when the doc is opened in place
- Child DOX Index entry format: `- [<relative-path>](<relative-path>) — <scope description>`
- Before editing or indexing a linked target, read it first (see Read Before Editing); a link must always point at a file that exists

## Style

- Keep docs concise, current, and operational
- Document stable contracts, not diary entries
- Put broad rules in parent docs and concrete details in child docs
- Prefer direct bullets with explicit names
- Do not duplicate rules across many files unless each scope needs a local version
- Delete stale notes instead of explaining history
- Trim obvious statements, repeated rules, misplaced detail, and warnings for risks that no longer exist

## Closeout

1. Re-check changed paths against the DOX chain
2. Update nearest owning docs and any affected parents or children
3. Refresh every affected Child DOX Index
4. Remove stale or contradictory text
5. Run `pnpm check:dox`, plus the verification named by the docs you touched
6. Report any docs intentionally left unchanged and why

`pnpm check:dox` ([scripts/check-dox.js](scripts/check-dox.js)) enforces the mechanical half of this
contract: dead links, missing or misordered sections, and a Child DOX Index that disagrees with the
tree. It cannot judge whether the prose is still true — that part is still the closeout's job.

## User Preferences

- Answers and work products should be high quality and verified as far as practical for the requested scope.
- Agents should choose and use relevant skills on their own when the request calls for them.
- Task queues, PRDs, planning files, and similar planning artifacts must be written in English unless the user explicitly asks for another language.
- In coding tasks, apply YAGNI: favor simple, concise solutions, including one-liners when they genuinely improve clarity without sacrificing quality, readability, maintainability, or design.
- DOX indexes and durable file references should use Markdown links to the referenced files whenever practical.
